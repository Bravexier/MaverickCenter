# Service des personnages (`client/serveur/`)

## Fichiers
- `serveur/index.mjs` (point d'entrée livré), `service.mjs` (HTTP, surveillance), `api.mjs` (routes), `fiches.mjs` (fiche ↔ lignes de la section 13), `base-vivante.mjs` (création, reconstruction, archives), `fiches-retraits.mjs` (R42), `livraison.mjs` (Astro), `structure-sur-place.mjs` (appliquer les migrations sur place, essai sur une copie, bilan `maverick-structure/1`), `essai-de-structure.mjs` (essai avant installation ; option `essaiDeStructure` de `demarrerService`), `essai-dans-l-ombre.mjs`, `dev.mjs` (`npm run serveur`, jamais livré), `acces.mjs` et `acces-routes.mjs` (accès au site de dev).
- `serveur/atelier.mjs` : l'atelier du site de dev (option `atelier` de `demarrerService`, `service.atelier`), skill `zone-hebergement-atelier`.
- `src/lib/fiche-format.mjs` : format d'une fiche, partagé avec les pages (sans dépendance).
- Édition des règles (`/api/edition/`, `serveur/edition*.mjs`) : skill `zone-edition`. Conteneurs, nginx, installateurs : skill `zone-hebergement`. Maintenance : skill `zone-maintenance`. Page « Mise à jour » : skill `zone-mise-a-jour`. `/api/v1/` : skill `zone-api-rest`. Métriques et page Debug : skill `zone-debug-metriques`. Tables de la section 13 : skill `zone-fiches-base`. `POST /api/classeur/` et `GET /api/tipeee/` (les deux sorties vers l'extérieur) : skill `zone-service-sorties`. Extrait du contenu, attestation, empreintes : skill `zone-service-extrait`.

## À lire
- `docs/serveur.md` : « Le code », « La base vivante (`db/`) » (reconstruction, retraits, conversions, sauvegarde), « L'API » (routes, format JSON d'une fiche, refus, repli sur une base d'avant), « Hébergement », « Développement ».

## Ce que fait le service
- Node ≥ 22.13, `node:sqlite`, aucun paquet npm. Sous `/api/` : prétirés (liste, lecture, création, modification avec `version`, suppression), portrait, contrôles de `v_personnage_controle` (ils signalent seulement).
- Il écrit dans la base vivante `db/vivante.db` = copie de `site/donnees/maverick.db` + section 13, refaite seulement quand ce que les règles apportent change (fiches reprises ; archives dans `db/archives/`) : voir « Reconstruction ».
- À la reconstruction, un don, une spécialité, un sort (avec son livre), un métier ou une arme (R52) disparu est retiré des fiches avec une note datée (R42, `fiches-retraits.mjs`), liste dans `/api/etat`. Toute autre référence rompue : rien ne change, `/api/etat` dit pourquoi.
- Livré : `livraison.mjs` le copie dans `dist/_serveur/` avec `version.json` et `FICHIERS_JOINTS` (qui livre aussi toutes les migrations `.sql` et `schema.sql`). Prétirés seulement.
- `/api/etat` (site de dev) : `modifications.en_attente`, `.conflit` et `.lots_en_conflit` ne comptent que les lots à résoudre.

## Invariants
- Le service n'importe que `node:…` et des chemins relatifs (`modulesDuServeur` de `serveur/livraison.mjs`, testé). `tools/build-artifact.mjs` n'emporte pas `_serveur/`. Il emporte `lib/fiche-moteur.mjs` (pur) par `lib/poids-portable-db.mjs`, jamais `lib/fiche-regles.mjs`.
- Une écriture exige `Content-Type: application/json` et refuse un autre `Sec-Fetch-Site`.
- Les adresses de l'API finissent par « / » (`/api/personnages/<id>/`) : en développement, Astro (`trailingSlash: 'always'`) refuse les autres.
- `traiter` (`serveur/api.mjs`) est synchrone, sauf `POST /api/classeur/`, `GET /api/tipeee/` et `GET /api/edition/extrait/`, qui rendent une promesse que `service.mjs` attend (une réponse détruite n'est plus écrite).
- Surveillance (`service.mjs`) : un changement compte vu deux fois de suite (`guetteur`). `version.json` changé : le service s'arrête (code 0), Docker le relance ; `maverick.db` changé : base vivante préparée (refaite ou non) ; `db/vivante.db` remplacée : rouverte.
- Une table ajoutée à la section 13 va dans `TABLES_FICHES` (`src/lib/fiche-format.mjs`, réexportée par `base-vivante.mjs`, donc dans `TABLES_VIVANTES` et dans `TABLES_INTERDITES` du journal) et, si elle cite `personnage`, dans `PARTIES_DE_FICHE` ou `HORS_FICHE` (`fiche-format.mjs`). Les tests `serveur-*` le vérifient contre `schema.sql`.
- Une clé étrangère de plus vers `metier`, `specialite`, `capacite`, `sort`, `arme` ou `classe_annexe_entree` va dans `RETRAITS` (`serveur/fiches-retraits.mjs`, testé).
- Une table retirée de la section 13 va dans `TABLES_RETIREES` (`fiche-format.mjs`) avec sa conversion (`CONVERSIONS`, `base-vivante.mjs`) : sinon ses lignes se perdent sans erreur.
- Des lignes que ses nouvelles règles refusent ne sont pas recopiées : `LIGNES_ECARTEES` de `base-vivante.mjs` (un prédicat SQL valable sur l'ancienne et la nouvelle forme, et ce qu'on note).
- Une colonne retirée de la section 13 va dans `COLONNES_RETIREES` (`fiche-format.mjs` : la base vivante la perd sans bloquer, une fiche qui la porte encore se lit sans elle) ; si elle porte une donnée à reprendre, aussi sa conversion dans `COLONNES_CONVERTIES` (`base-vivante.mjs`, quand l'ancienne base a la colonne).
- Les retraits et conversions ne passent jamais par le journal de l'édition : SQL direct (skill `zone-fiches-base`).

## Accès au site de dev (R275, option b : mot de passe pour modifier et lancer une mise à jour, lecture ouverte)
- `serveur/acces.mjs` : réglage `secrets/acces.json` (scrypt, SHA-256 de la clé de lecture, secret de session), sessions HMAC de 12 h, essais limités ; `serveur/acces-routes.mjs` : le classement des routes. Détail : `docs/serveur.md`, « Accès au site de dev ».
- Toute route nouvelle se classe dans `acces-routes.mjs` : ouverte, lecture (clé ou mot de passe), proposition ou écriture (mot de passe) ; une route inconnue est fermée comme une écriture, et `serveur-acces-routes.test.mjs` échoue sinon.
- Classe `proposition` : la même porte que `lecture` (clé ou mot de passe), pour déposer un lot de changements, refaire son essai et `POST /api/edition/lots/recalcul/` ; elle n'écrit que `lot_de_changements`, jamais le contenu. `GET …/annulation/` est en `lecture` ; appliquer, refuser et annuler (`POST …/annuler/`) un lot sont en `ecriture` ; toutes les routes `/api/edition/lots/` répondent 403 hors site de dev (skill `zone-edition-lots`).
- Réglage absent : tout est ouvert comme avant. La production n'est jamais concernée. Fiches de joueur, comptes et groupes ne sont jamais ouverts une fois le mot de passe posé.
- `/api/etat` sans droit de lecture est masqué : jamais `retraits` ni `base.erreur` détaillée.
- La clé passe par `X-Maverick-Cle` ou `X-Maverick-Key` (le formulaire de clé des sessions Claude exige un nom finissant par `key`), seulement ces deux (`ENTETES_CLE`, `serveur-acces.test.mjs`) : tout nouveau nom passe par là. Caddy et nginx effacent `Authorization`. Navigateur : cookie `maverick_acces`. Aucun secret dans le journal, les métriques ni la page Debug.

## Atelier du site de dev (`serveur/atelier.mjs`)
- Le service tient à jour l'extrait de l'atelier dans le dépôt de l'atelier, monté sur `/atelier-depot` (`contenu-<version>.db`), jamais sous `db/essai-de-structure/` (que le service efface au premier passage) (skill `zone-service-extrait`).
- Il lit les rapports de root montés sur `/atelier` en lecture seule, un fichier à la fois, forme et taille validées. Le champ `bilan` (`maverick-atelier-bilan/1`, verdicts `tient`, `tient_tout_juste`, `ne_tient_pas`, `journee_incomplete`) est calculé à chaque lecture par `src/lib/atelier-bilan.mjs` (module pur, livré avec le service) ; ses `SEUILS` sont des choix techniques, exposés et réglables. États : `pas_d_atelier`, `non_installe`, `en_attente`, `en_cours`, `rapport` (route et page : skill `zone-debug-metriques`).

## Reconstruction
- La base vivante n'est refaite que si `serveur/empreintes.mjs#empreinteLogique` change (SQL de tout `sqlite_master`, tables de fiches comprises ; `user_version` ; lignes de toutes les tables hors `TABLES_VIVANTES`) ou si `VERSION_DE_LA_RECONSTRUCTION` (`base-vivante.mjs`) change. Dans le doute (empreinte absente, calcul en échec), elle est refaite.
- **Tout changement de la logique de `preparerBaseVivante` (CONVERSIONS, LIGNES_ECARTEES, COLONNES_CONVERTIES, retraits R42, armures R165) augmente `VERSION_DE_LA_RECONSTRUCTION`** : sinon il attend la livraison suivante des règles.
- `preparerBaseVivante` note dans `migration_recue` les migrations reçues (`reconstruction` ou `sur_place` : skill `base-sqlite`) ; l'échec de cette note est journalisé, sans arrêter la reconstruction. `migration_recue` n'entre pas dans le compte de l'archivage. Sur le site de dev, `vivante.json` garde `tables_regles`.
- `VERSION_DE_LA_RECONSTRUCTION` reste à 1 malgré cette note : aucune reconstruction n'est forcée sur la production.
- Archive : `vivante-<horodatage>-v<version>.db` (`-inconnue` si la version manque) ; les anciens noms sont purgés avec les nouveaux.

## Conversions en place
Chaque conversion est décrite dans `docs/serveur.md` (« La base vivante », « L'API »). Une fiche reçue avec l'ancienne forme est convertie (`sansPartiesRetirees`), jamais refusée, sauf mélange avec les nouvelles clés (409).
- `personnage_progression` (0045) : la somme `gains_sante` / `gains_chakra`.
- `personnage_armure` (0055, R95) : la première pièce dans l'ordre des emplacements (`armureDesArmures`) devient l'armure de `personnage` ; chaque autre pièce, et la pièce gardée qui perd une amélioration ou un élément (`retraitsDeLArmure`), est un retrait noté et listé dans `/api/etat` avec ceux de R42 (`noterLesRetraits`). Liste `armures` reçue : `lignesDesPiecesRetirees` (ses lignes s'ajoutent aux notes enregistrées sans toucher au texte du joueur ; avec les nouvelles clés : 409).
- `personnage_bouclier_materiau` (0060, R96) : le premier rang devient `personnage.bouclier_materiau_id`, les autres sont notés (`bouclier_materiaux` reçu avec les nouvelles clés : 409).
- `personnage_accessoire` (0060, R97) : la Ceinture, « Autre » et l'effet hors table seul écartés ; un nom ou un effet hors table perdus (`COLONNES_RETIREES`) notés.
- Conversions de 0062 (R104) et 0066 (`nm_cadeau`, R118) : `docs/serveur.md`.
- Armure de R165 (0080 ; de base OU élémentaire) : `retirerLesArmuresHorsRegle` (`fiches-retraits.mjs`), à **chaque reconstruction** (idempotente) et **chaque enregistrement** (dans la transaction), **joueurs compris** : armure + élément → l'élément devient l'armure ; armure « Familier » ; armure élémentaire d'une magie ni innée ni acquise ; armure trop lourde pour le poids portable (R165 (6), (7)). Une fiche reçue avec les deux armures est **convertie** (R165 (8) : `sansPartiesRetirees` avec `armureDouble: false`). Natures dans `NATURES_DE_L_ARMURE`, textes **identiques** à la migration 0080 (`serveur-armure-elementaire`).
  - Le poids : `lib/poids-portable-db.mjs#poidsPortableDeLaBase` rejoue le calcul du moteur en quelques requêtes. **Jamais `chargerReglesDeFiche` dans le service** (près d'un Mo ; un cache serait faux : le site de dev modifie les règles). Une entrée de plus à `poidsPortableDe` du moteur se lit aussi dans `poids-portable-db.mjs` (`serveur-poids-portable` compare). Base sans ce qu'il lit (`COLONNES_LUES`) : null, rien de retiré. L'option `poidsPortable` de `preparerBaseVivante` et `enregistrerFiche` remplace le calcul (tests).
- `personnage_arme` (0081, R167) : un seul `amelioration_id` (`amelioration_elementaire_id` dans `COLONNES_RETIREES`) ; une arme du catalogue qui porte un élément est écartée (`LIGNES_ECARTEES`) puis écrite convertie (`COLONNES_CONVERTIES`), une ligne datée par arme, nature `arme_elementaire` ; fiche reçue : `armesDAvant`. Un matériau ou un `type_degats_choisi` sur une arme du catalogue, ou ni arme ni arme élémentaire : `400` (`CHECKS_DE_LA_FICHE`). R52 ne vise jamais une arme élémentaire.
- `personnage_maitrise_arme` et `personnage_acquis_choix.arme_famille_id` (0076, R148, R152, R153) : « Tout remettre à choisir », anciens dés et arme choisie notés en **une ligne par fiche** (nature `maitrises_armes`, la dernière de `ORDRE_DES_NATURES`). Envoyés avec `maitrise_choix` : 409.
- `personnage` : toute colonne ajoutée (le Mode Hyper, 0084, R172) entre dans `DEPART_DES_COLONNES_AJOUTEES.personnage` ; `ficheVide` porte les deux cases à 0, le compteur absent (au maximum). Même règle pour `personnage_sort` (0086, 0089, R182 : `DEPART_DES_COLONNES_AJOUTEES.personnage_sort` porte `prepare_hyper: 0, prepare_cent: 0, prepare_critique: null`), dont chaque contrainte `personnage_sort_prepare_*` a son message en `400`.
- `personnage_action_usage` (0085, R173) : partie `actions_usage: [{ action_id, restants }]`. Base d'avant 0085 : lue vide, liste non vide refusée.
- `personnage_don_obtenu` (0088, R181) : partie `dons_obtenus: [{ source, entree_id }]` (`PARTIES_DE_FICHE`) ; base d'avant 0088 : lue vide, liste non vide refusée ; doublon en `400` (`UNIQUES_DE_LA_FICHE`). `RETRAITS` a **deux entrées** (vers `classe_annexe_entree` et vers `capacite`, sans ON DELETE) : nature `don_obtenu` (`entree` ou `don`), joué à l'édition et à la reconstruction.
- `personnage_specialisation_magie` (0118, R236) : partie `specialisations_magie: [{ magie_id, specialisation_id }]`. `RETRAITS` y a une entrée à **clé composée** (`colonnes`) ; nature `specialisation_magie`, après `specialite` dans `ORDRE_DES_NATURES` (la magie redevient « à choisir »). Le retrait joue à la reconstruction seule.
- `personnage_sort.nm_livre` (0082, R169) : chaque sort à `nm_livre = 1` devient un livre de `personnage_livre_sort` (`COLONNES_CONVERTIES`), le NM ne change pas (`livres_sorts` avec un `nm_livre` à 1 : 409). `RETRAITS` a **deux entrées pour `sort`** (la liste, et `personnage_livre_sort`, sans ON DELETE) : le livre part avec le sort retiré par R42, y compris un livre seul ; `appliquer` parcourt toutes les entrées qui visent l'élément.

## Structure de la base (R274, R275)
- Tant que `db/source` n'existe pas (la base du site de dev n'est pas encore la source), rien ne migre la vraie base : un essai de structure qui échoue n'arrête ni le site ni l'installation. Détail : `docs/serveur.md`.
- Les copies d'essai sont toujours effacées : purge à l'ouverture, et dans le `catch` d'un fil mort.
- La base n'est pas en WAL : un `VACUUM INTO` fait attendre les écritures.
- Les messages « structure : … » du journal du service sont rangés en catégorie `base`. Page Debug : skill `zone-debug-metriques` ; installateur : skill `zone-hebergement`.
