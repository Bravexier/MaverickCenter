# Mise à jour et maintenance

## Fichiers
- Page : `client/src/pages/mise-a-jour.astro` (menu Outils), script `src/scripts/mise-a-jour.mjs`, CSS `styles/mise-a-jour/`.
- Lignes en conflit sur la page : rendu pur `lib/conflits-rendu.mjs` (`htmlDesConflits`, `htmlDuLot`, `htmlDuConflit`, `texteDeLaVersion`, `raisonDuChoix`, `raisonDuConflit`, `colonnesDeLaSaine`, `erreurDeSaisie`, `corpsDeLaResolution`, `messageDeResolution`), posé et envoyé par `src/scripts/mise-a-jour.mjs` (seul script à l'importer).
- Notes de version : `lib/notes-de-version.mjs` (`comparerBases`, `DEFINITIONS`, `TABLES_LUES`, `TABLES_DES_NOTES`, `resume`, `detail`), `lib/notes-de-version-sens.mjs` (couleurs R29), `lib/notes-de-version-rendu.mjs` (`lancementAffiche`).
- Service : `serveur/notes-de-version.mjs` (note en préparation, lot figé, états du lancement, `lireLot`, `modifierLancement`, `actualiserLancement`, `creerGithub`).
- Lots du journal en conflit : `serveur/edition-conflits.mjs` (`conflitsDuJournal`, `examinerLeLot`, `resoudreLeConflit`, `compterLesConflits`, `libelleDeLigne`, `raisonLisible`, `detailLisible`), routes `GET` / `POST /api/mise-a-jour/conflits/` ; parcours sans arrêt au premier conflit : `serveur/edition-journal.mjs#parcourirUnLot`, `evaluerUne`, `rompuesDuLot`.
- Scripts : `scripts/db-reference.mjs` (base de master), `scripts/mise-a-jour-regles.mjs` (rejeu du lot sur `data/rows`, `TABLES_DE_LA_NOTE`, `notesEnAttente`), `scripts/mise-a-jour-github.mjs` (phases du workflow, `CONTROLES`, `CONTROLES_DE_LA_CI`), `scripts/mise-a-jour-simulation.mjs` (lot synthétique de la CI).
- Workflow : `.github/workflows/mise-a-jour.yml` ; job `simulation-de-mise-a-jour` de `.github/workflows/ci.yml`.
- Maintenance : `serveur/maintenance.mjs` (`annonceDuLancement`, `etatDeMaintenance`, `DUREE_MAX_MAINTENANCE`), `pages/maintenance.astro`, `scripts/maintenance.mjs`, `lib/maintenance-retour.mjs`, `styles/maintenance/` ; script en ligne de `layouts/Base.astro`.

## Choix du propriétaire
- En production (et partout sans service) : la note de version de la dernière livraison (tables `note_version`, `note_version_ligne`, section 15) puis l'historique.
- Sur le site de dev, en plus : la note en préparation (la base de master construite au build, `donnees/reference.db`, comparée à la base vivante : `comparerBases`), le champ libre (`note_version_brouillon`, section 14), les boutons « Simulation de mise à jour » (rien n'est poussé) et « Effectuer la mise à jour » (lot figé → workflow `mise-a-jour.yml` → lot rejoué sur `data/rows` sans toucher d'autres tables, PR vers dev fusionnée si verte, puis livraison dev → master).
- La case « Version majeure » à côté du titre « Mise à jour en préparation : VX.Y+1 » (demande du 2026-10-22) : cochée après confirmation (décochée sans), la version en préparation devient VX+1.0 ; elle ne déclenche rien, « Effectuer la mise à jour » reste le seul déclencheur. Colonne `note_version_brouillon.majeure` (migration `0070` : 1 cochée, NULL décochée), `POST /api/mise-a-jour/majeure/`, `enregistrerMajeure` ; figée avec le lot (`409`), gardée s'il est annulé, décochée quand la livraison vide le brouillon. `actualiserLancement` ne vide le brouillon qu'au passage d'un lancement annulé dont le lot est entré dans dev quand même, jamais ensuite (le brouillon est alors celui de la mise à jour suivante).
- La production est la base de master (décision du propriétaire).
- Pas de protection du bouton avant la connexion Discord (décision du propriétaire), case « Version majeure » comprise : le risque qu'un visiteur du site de dev fasse partir une version majeure est accepté (2026-10-22), à revoir avec l'authentification Discord.
- Une mise à jour sans modification ni texte reste refusée (« Rien à livrer », `figerLot`), même case cochée : un passage en version majeure seul demande un texte dans le champ libre (choix du 2026-10-22).
- La note de la V0.2 ne liste rien ; son texte dit « Import initial depuis les sources historiques » (migration `0028`, `historique_modification` gardé).
- L'encart « Dernier lancement » ne parle que de la version en préparation, sauf s'il pèse encore sur la page (`lancementAffiche`).
- Le bandeau du site de dev (`Base.astro`) dit « Serveur de dev. » et renvoie à cette page.
- Conflits (demande du propriétaire du 2026-10-22 : « Après les listes de modifications, montrer les lignes en conflits. 1. Pour chaque conflit, montrer les deux versions 2. Laisser le choix entre 1, 2, ou 3 pour saisir à la main ce qui remplace les deux. ») : après les listes de la note en préparation, les lots en conflit ; version 1 = ce que le site de dev avait écrit, version 2 = les règles livrées (ou « ligne supprimée ») ; 1 garde la version 1, 2 la règle livrée, 3 une valeur saisie (type de la colonne, contrôles de l'éditeur). Site de dev seulement.
- La section des conflits (`[data-nv-conflits]`, dernière de la note en préparation, après `.nv-dev__liste`) : le bilan dit « N lot(s) en conflit ne part (partent) pas avec cette mise à jour » ; par lot, sa date, son résumé, la raison du rejeu (« Au rejeu : » suivi de `detail_lisible`, jamais `detail` : ni id du lot, ni clé JSON, ni nom de colonne technique ; rien sans `detail_lisible` ; tests `conflits-rendu`, `mise-a-jour-conflits`), ses modifications saines (« repartira telle quelle », « déjà dans les règles livrées »…), puis chaque conflit : version 1 et version 2 côte à côte, en texte (un long texte se lit en entier, retours à la ligne gardés), leurs différences mot à mot quand ce sont deux textes (`diffMots`), les choix 1, 2, 3, un choix impossible grisé avec sa raison ; le 3 ouvre une saisie selon `saisie.type` (texte et markdown : zone de texte ; entier, réel : bornes ; choix : `saisie.choix` ou la liste de `GET /api/edition/listes/` ; ligne et catégories : une ligne), la version 1 en départ ; « Résoudre ce lot » attend un choix par conflit et les contrôles simples (obligatoire, nombre, bornes), puis le message de la réponse ; un 409 repose le lot à jour (les choix qui y valent restent). Jamais d'HTML reçu posé : l'aperçu de l'éditeur (`apercu`) n'est pas montré, le Markdown de la version 1 se lit tel quel.
- La section est gardée d'un rendu de la note à l'autre (le suivi d'un lancement la refait toutes les 15 s, la case « Version majeure » aussi) : les choix en cours ne se perdent pas. Sans lot en conflit (`en_conflit.lots` à 0), ni section ni requête des conflits. Rien en production ni dans la version portable (le script n'y tourne pas : `edition` faux ou absent).
- Maintenance en cours (demande du propriétaire) : une vraie mise à jour lancée, les deux sites partent vers `/maintenance/` (menus grisés et inertes, « En travaux, merci de revenir dans quelques minutes »), et chaque serveur rouvre indépendamment dès qu'il a sa nouvelle version.

## Invariants
- Référence : `scripts/db-reference.mjs` construit la base de master depuis `git archive origin/master` (`donnees/reference.db`). La CI et la livraison font `git fetch … master` avant le build. Sans master, la page dit que la référence manque. Rien de tout cela en `SITE_MODE=prod` ni dans la version portable.
- La liste ne compare que les colonnes de `TABLES` (`lib/edition-modele.mjs`, skill `zone-edition`) ; le reste en est dérivé.
- Une couleur vient de R29 et de rien d'autre (`notes-de-version-sens.mjs`) ; tout cas douteux reste neutre.
- Domaines : sorts, magies, classes, races, métiers, guide, Codex, bestiaire, armes, armures, composants, chronologie, mots-clés, équipement. C'est la contrainte CHECK de `note_version_ligne.domaine` (migrations `0032`, `0034`, `0040`, `0043`, `0046`, `0056`) : un domaine nouveau demande une migration.
- Une table nouvelle dans `TABLES` n'est listée qu'avec sa définition (`DEFINITIONS`, `TABLES_LUES`).
- `detail` : une ligne qui n'existe qu'avec une autre (rubrique, butin) n'est listée que pour un champ modifié. `resume` : un contenu absent de la production est dit en une ligne.
- `scripts/mise-a-jour-regles.mjs` refuse d'écrire un fichier de `data/rows` hors des tables du journal et de la note (`TABLES_DE_LA_NOTE`), plus celles que le rejeu écrit au-delà du journal (`tablesCompletees`). Un fichier de `data/rows` qui n'est pas tel que l'exporteur l'écrit bloque donc une mise à jour.
- `scripts/mise-a-jour-github.mjs#tablesDuLot` (la liste blanche du commit) recopie la règle de `tablesCompletees` : `page_tag`, `page` et les tables à balises pour un mot-clé retiré ; `mot_cle` pour une étiquette d'avant 0043 ; les sources de maîtrise d'arme (`TABLES_DES_SOURCES_DE_MAITRISE`) pour un lot qui touche `classe`, `classe_maitrise_arme` ou `capacite` (skill `zone-edition`).
- Une vraie mise à jour retire les notes `exemple = 1` qui resteraient (lorem ipsum, migration `0023`).
- `[V: X+1]` n'est jamais repris d'un texte (corps des PR, commentaires : `neutraliserMarqueur`) ; il n'est posé que dans le titre de la PR de livraison d'un lot `majeure` (`titreLivraison`), et la livraison s'arrête si une PR de livraison le porte sans que le lot le demande, ou l'inverse (`desaccordMajeure`, `MAJEURE_AJOUTEE`, `MAJEURE_RETIREE`). La note du lot est alors la X+1.0 (`versionDeLivraison(…, { majeure })`, même règle que `planifier`).
- Le job `preparer` lance `npm test` après avoir écrit la note du lot dans `data/rows` (pas encore sur master). Le job CI `simulation-de-mise-a-jour` applique de même un lot synthétique (`scripts/mise-a-jour-simulation.mjs` : le service fait de vraies modifications et fige le lot) puis les mêmes contrôles (`CONTROLES`, épinglés par `test/mise-a-jour-simulation.test.mjs`).
- Un test qui lit `data/rows` tient avec une note en attente : copie sans elle (`test/aide-mise-a-jour.mjs#copieSansNoteEnAttente`), version libre (`versionLibre`), balayages qui sautent la section 15 (`TABLES_DES_NOTES`). Détail : skill `tests-conventions` et `docs/serveur.md`.
- Un lot en conflit ne part jamais avec une mise à jour (`journalExporte`) et ne bloque rien ; il reste « à résoudre » (`resolu_le` NULL) jusqu'à sa résolution, qui écrit UN nouveau lot normal du journal (saines, choix 1 et 3 par l'opération « modifier » de l'édition) et marque l'ancien (`resolu_le`, `resolu_par`, `resolution`, migration 0072) sans l'effacer : ses lignes restent `conflit` (trace). Tout au choix 2 sans rien de sain : aucun lot, `resolu_par` NULL.
- Rien de technique sur la page : le service fournit les textes, la page les affiche (elle n'importe pas `TABLES`). `libelle` d'une ligne sans JSON (`libelleDeLigne` : nom ou titre, sinon l'id de la clé, sinon ce que désigne sa clé composée — la ligne citée par son nom lu dans la base, sinon son id, un rang dit « n° N » ; jamais un nom inventé) ; `raison_lisible` de chaque conflit à côté de `raison` (la trace : `raisonLisible`, libellés de `TABLES`, une colonne sans libellé garde son nom) ; `colonnes_libelles` d'une saine partielle à côté de `colonnes`. La page les affiche (`raisonDuConflit`, `colonnesDeLaSaine`) et se replie sur `raison` et `colonnes` pour une réponse ancienne ; une ligne entière (version `ligne`, `valeurs`, `suppression`) nomme ses colonnes par `libelles` de la version quand le service le donne (sinon leur nom) ; une valeur objet se lit « clé : valeur », jamais en JSON (`texteDeValeur`). Tests `conflits-rendu` et `mise-a-jour-conflits` sur la fixture : ni `{"` dans la section, ni nom de colonne à « _ » qui a un libellé dans `TABLES` hors du contenu des versions.
- La fixture `test/fixtures/conflits-diagnostic.json` est le diagnostic du scénario de `serveur-edition-conflits`, recalculé par `MAVERICK_ECRIRE_FIXTURE=1 node --test test/serveur-edition-conflits.test.mjs` (longs textes raccourcis), jamais écrite à la main ; le test compare ses textes lisibles au diagnostic.
- La raison du rejeu d'un lot : `detail` (la trace des lignes du lot, jamais réécrite) et `detail_lisible` (`detailLisible` : sans l'id du lot, la ligne dite par la légende de son conflit ou de sa saine de même clé, sinon `libelleDeLigne`, colonnes et tables par leur libellé de `TABLES`) ; la page montre `detail_lisible`.
- Le diagnostic (GET) est recalculé sur la base vivante dans un savepoint toujours annulé (exception assumée à la lecture seule) ; la résolution exige son `empreinte` (sinon 409) et refait le même parcours (sinon 409). Une ligne qui n'existe plus, une forme ancienne, une clé étrangère rompue : seul le choix 2. Une ligne de détail n'est jamais un conflit : elle suit sa source (choix 2 : re-dérivée, sans toucher au corps de la page). Les lignes des sources de maîtrise d'arme (`maitrise_arme_part`, ses options, `capacite_nm_gagne`) ne sont pas parcourues : refaites par le lecteur après les choix pour toutes les classes et tous les dons du lot, notées dans le nouveau lot (`edition-maitrises.mjs#sourcesRefaitesParLaResolution`, skill `zone-edition`).
- `/api/etat` et la note en préparation (`en_conflit`) ne comptent que les lots à résoudre, par le même compte écrit une seule fois (`edition-conflits.mjs#compterLesConflits`, importé par `serveur/notes-de-version.mjs` : jamais une copie de sa requête, test `serveur-edition-conflits.test.mjs`).
- Seul le lot du lancement actuel est servi au workflow (`lireLot`, sinon `410`) ; un suivi revenu en retard n'écrase jamais un état plus récent (`modifierLancement`).
- Maintenance, « terminé » pour un serveur : la version qui tourne (celle du service, lue au démarrage) atteint la version cible X.Y du lot. Le serveur de test passe par la version de dev qui porte le lot, encore en maintenance.
- L'annonce ne vient que d'une vraie mise à jour (`envoi` → `termine`), jamais d'une simulation ni de `manuel` (la page « Mise à jour » doit rester ouverte pour en donner les valeurs). Le service du site de dev la publie (lot, version cible) dans le dossier partagé (`MAVERICK_MAINTENANCE`, le `maintenance/` du serveur normal monté dans les deux instances) ; la production la lit et n'écrit rien.
- Échec, annulation, « Lever la maintenance » ou 4 h (`DUREE_MAX_MAINTENANCE`) retirent l'annonce.
- La minuterie du site de dev suit le run et republie l'annonce : personne n'est sur ses pages, qui renvoient vers `/maintenance/`.
- Le script de chaque page (`Base.astro`, demande `/api/maintenance/`) est en ligne (aucun module partagé), absent de la version portable et de `/maintenance/`. `lib/maintenance-retour.mjs` ne ramène qu'à une page de ce site.
