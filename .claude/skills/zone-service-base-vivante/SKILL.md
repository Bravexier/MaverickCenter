# Base vivante des fiches (`client/serveur/base-vivante.mjs`)

Le service, l'API et l'accès : skill `zone-service`. Tables de la section 13 : skill `zone-fiches-base`.

## Invariants
- Une table ajoutée à la section 13 va dans `TABLES_FICHES` (`src/lib/fiche-format.mjs`, réexportée par `base-vivante.mjs`, donc dans `TABLES_VIVANTES` et dans `TABLES_INTERDITES` du journal) et, si elle cite `personnage`, dans `PARTIES_DE_FICHE` ou `HORS_FICHE` (`fiche-format.mjs`). Les tests `serveur-*` le vérifient contre `schema.sql`.
- Une clé étrangère de plus vers `metier`, `specialite`, `capacite`, `sort`, `arme` ou `classe_annexe_entree` va dans `RETRAITS` (`serveur/fiches-retraits.mjs`, testé).
- Une table retirée de la section 13 va dans `TABLES_RETIREES` (`fiche-format.mjs`) avec sa conversion (`CONVERSIONS`, `base-vivante.mjs`) : sinon ses lignes se perdent sans erreur.
- Des lignes que ses nouvelles règles refusent ne sont pas recopiées : `LIGNES_ECARTEES` de `base-vivante.mjs` (un prédicat SQL valable sur l'ancienne et la nouvelle forme, et ce qu'on note).
- Une colonne retirée de la section 13 va dans `COLONNES_RETIREES` (`fiche-format.mjs` : la base vivante la perd sans bloquer, une fiche qui la porte encore se lit sans elle) ; si elle porte une donnée à reprendre, aussi sa conversion dans `COLONNES_CONVERTIES` (`base-vivante.mjs`, quand l'ancienne base a la colonne).
- Les retraits et conversions ne passent jamais par le journal de l'édition : SQL direct (skill `zone-fiches-base`).

## Reconstruction
- La base vivante n'est refaite que si `serveur/empreintes.mjs#empreinteLogique` change (SQL de tout `sqlite_master`, tables de fiches comprises ; `user_version` ; lignes de toutes les tables hors `TABLES_VIVANTES`) ou si `VERSION_DE_LA_RECONSTRUCTION` (`base-vivante.mjs`) change. Dans le doute (empreinte absente, calcul en échec), elle est refaite.
- **Tout changement de la logique de `preparerBaseVivante` (CONVERSIONS, LIGNES_ECARTEES, COLONNES_CONVERTIES, retraits R42, armures R165) augmente `VERSION_DE_LA_RECONSTRUCTION`** : sinon il attend la livraison suivante des règles.
- `preparerBaseVivante` note dans `migration_recue` les migrations reçues (`reconstruction` ou `sur_place` : skill `base-sqlite`), sans arrêter la reconstruction si la note échoue ; `migration_recue` n'entre pas dans le compte de l'archivage. Sur le site de dev, `vivante.json` garde `tables_regles`.
- Archive : `vivante-<horodatage>-v<version>.db` (`-inconnue` si la version manque) ; les anciens noms sont purgés avec les nouveaux.

## Conversions en place
Chaque conversion est décrite dans `docs/serveur.md` (« La base vivante », « L'API »). Une fiche reçue avec l'ancienne forme est convertie (`sansPartiesRetirees`), jamais refusée, sauf mélange avec les nouvelles clés (409).
- `personnage_progression` (0045) : la somme `gains_sante` / `gains_chakra`.
- `personnage_armure` (0055, R95) : la première pièce (`armureDesArmures`) devient l'armure de `personnage` ; chaque autre pièce, et la pièce gardée qui perd une amélioration ou un élément (`retraitsDeLArmure`), est un retrait noté et listé dans `/api/etat` avec ceux de R42 (`noterLesRetraits`). Liste `armures` reçue : `lignesDesPiecesRetirees` (ajoutées aux notes sans toucher au texte du joueur ; avec les nouvelles clés : 409).
- `personnage_bouclier_materiau` (0060, R96) : le premier rang devient `personnage.bouclier_materiau_id`, les autres sont notés (`bouclier_materiaux` reçu avec les nouvelles clés : 409).
- `personnage_accessoire` (0060, R97) : la Ceinture, « Autre » et l'effet hors table seul écartés ; un nom ou un effet hors table perdus (`COLONNES_RETIREES`) notés.
- Conversions de 0062 (R104) et 0066 (`nm_cadeau`, R118) : `docs/serveur.md`.
- Armure de R165 (0080 ; de base OU élémentaire) : `retirerLesArmuresHorsRegle` (`fiches-retraits.mjs`), à **chaque reconstruction** (idempotente) et **chaque enregistrement** (dans la transaction), **joueurs compris** : armure + élément → l'élément devient l'armure ; armure « Familier » ; armure élémentaire d'une magie ni innée ni acquise ; armure trop lourde (R165 (6), (7)). Une fiche reçue avec les deux armures est **convertie** (R165 (8) : `sansPartiesRetirees` avec `armureDouble: false`). Natures dans `NATURES_DE_L_ARMURE`, textes **identiques** à la migration 0080 (`serveur-armure-elementaire`).
  - Le poids : `lib/poids-portable-db.mjs#poidsPortableDeLaBase` rejoue le calcul du moteur en quelques requêtes. **Jamais `chargerReglesDeFiche` dans le service** (près d'un Mo ; un cache serait faux : le site de dev modifie les règles). Une entrée de plus à `poidsPortableDe` du moteur se lit aussi dans `poids-portable-db.mjs` (`serveur-poids-portable` compare). Base sans `COLONNES_LUES` : null, rien de retiré. L'option `poidsPortable` de `preparerBaseVivante` et `enregistrerFiche` remplace le calcul (tests).
- `personnage_arme` (0081, R167) : un seul `amelioration_id` (`amelioration_elementaire_id` dans `COLONNES_RETIREES`) ; une arme du catalogue qui porte un élément est écartée (`LIGNES_ECARTEES`) puis écrite convertie (`COLONNES_CONVERTIES`), nature `arme_elementaire` ; fiche reçue : `armesDAvant`. Un matériau ou `type_degats_choisi` sur une arme du catalogue, ou ni arme ni arme élémentaire : `400` (`CHECKS_DE_LA_FICHE`). R52 ne vise jamais une arme élémentaire.
- `personnage_maitrise_arme` et `personnage_acquis_choix.arme_famille_id` (0076, R148, R152, R153) : « Tout remettre à choisir », anciens dés et arme choisie notés en **une ligne par fiche** (nature `maitrises_armes`, la dernière de `ORDRE_DES_NATURES`). Envoyés avec `maitrise_choix` : 409.
- `personnage` : toute colonne ajoutée (le Mode Hyper, 0084, R172) entre dans `DEPART_DES_COLONNES_AJOUTEES.personnage` ; `ficheVide` porte les deux cases à 0, le compteur absent (au maximum). Même règle pour `personnage_sort` (0086, 0089, R182 : `DEPART_DES_COLONNES_AJOUTEES.personnage_sort` porte `prepare_hyper: 0, prepare_cent: 0, prepare_critique: null`), dont chaque contrainte `personnage_sort_prepare_*` a son message en `400`.
- `personnage_action_usage` (0085, R173) : partie `actions_usage: [{ action_id, restants }]`. Base d'avant 0085 : lue vide, liste non vide refusée.
- `personnage_don_obtenu` (0088, R181) : partie `dons_obtenus: [{ source, entree_id }]` (`PARTIES_DE_FICHE`) ; base d'avant 0088 : lue vide, liste non vide refusée ; doublon en `400` (`UNIQUES_DE_LA_FICHE`). `RETRAITS` a **deux entrées** (vers `classe_annexe_entree` et vers `capacite`, sans ON DELETE) : nature `don_obtenu` (`entree` ou `don`), joué à l'édition et à la reconstruction.
- `personnage_specialisation_magie` (0118, R236) : partie `specialisations_magie: [{ magie_id, specialisation_id }]`. `RETRAITS` y a une entrée à **clé composée** (`colonnes`) ; nature `specialisation_magie`, après `specialite` dans `ORDRE_DES_NATURES` (la magie redevient « à choisir »). Le retrait joue à la reconstruction seule.
- `personnage_sort.nm_livre` (0082, R169) : chaque sort à `nm_livre = 1` devient un livre de `personnage_livre_sort` (`COLONNES_CONVERTIES`), le NM ne change pas (`livres_sorts` avec un `nm_livre` à 1 : 409). `RETRAITS` a **deux entrées pour `sort`** (la liste, et `personnage_livre_sort`, sans ON DELETE) : le livre part avec le sort retiré par R42, y compris un livre seul ; `appliquer` parcourt toutes les entrées qui visent l'élément.
