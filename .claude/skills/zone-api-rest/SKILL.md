# API REST `/api/v1/`

## Fichiers
- Registre pur : `client/src/lib/ressources.mjs` (son en-tête est le contrat du format ; `HORS_RESSOURCE`, `OPERATIONS_DU_LOT`, `capacitesDe`) et ses 8 modules `src/lib/ressources/<module>.mjs` (`creation`, `regles`, `magie`, `equipement`, `artisanat`, `univers`, `bestiaire`, `wiki`).
- Routeur générique : `client/serveur/ressources.mjs` (`TRADUCTIONS` : une requête traduite en opération du lot).
- Description OpenAPI 3.1 : `client/serveur/openapi.mjs`, servie à `/api/v1/openapi.json`. Elle décrit tout le service : une route ajoutée à `serveur/api.mjs` (et à son en-tête) y est décrite avec ses méthodes (`cheminsDuService`, test `serveur-api-v1` qui lit l'en-tête).

## À lire
- `docs/api.md` : « Principes », « Adresses », « Lire », « Écrire » (opérations du lot), « Codes de réponse », « Ressources par module », « Rendre une ressource modifiable » (la recette), « Tests ».
- `docs/serveur.md`, « API REST `/api/v1/` et page Debug (site de dev) ».

## Choix du propriétaire
- Un CRUD pour tous les éléments du jeu (demande du propriétaire).
- Site de dev seulement : en production, tout `/api/v1/` répond `403`, lectures comprises (décision du propriétaire du 2026-10-15 : la base n'est ouverte que par le front). Le `403` passe avant tout le reste (`service.edition` faux).

## Invariants
- Une ressource n'est qu'une description dans le registre (`lib/ressources/<module>.mjs`, au format de l'en-tête de `lib/ressources.mjs`). Chaque table de la base y est rangée une fois et une seule : ressource, sous-ressource, extension, dérivée ou `HORS_RESSOURCE`.
- Une table ajoutée à `data/schema.sql` : la ranger dans le registre, ou la mettre dans `HORS_RESSOURCE` avec sa raison (`test/ressources-registre.test.mjs` l'exige). Une dérivée n'a qu'un parent : une table dont les lignes viennent de deux ressources (`maitrise_arme_part`, `maitrise_arme_part_famille` : une ligne de classe ou un don, migration 0076) va dans `HORS_RESSOURCE` (`ressources/creation.mjs`) ; `capacite_nm_gagne` est une dérivée de `dons-de-classe`. `capacite_variable` (la magie que vise un don « Variable », R181) en est une aussi, écrite par le service d'édition à la création d'un don et au changement de type (`zone-edition`) ; le PATCH d'un don accepte la clé `magie` (`CHAMPS_HORS_COLONNES`, catalogue `hors_colonnes`). `capacite_npm_plafond` et `capacite_condition_emplacements` (dérivées de `dons-de-classe`) et `magie_npm_plafond` (dérivée de `magies`) : R188, R189, migration 0097 : créées par la migration seulement (le service les retire avec leur don). `classe_annexe_entree` est la sous-ressource `entrees-du-tableau` de `classes/`, en lecture seule ; `regles_onglet` est la ressource `onglets-des-regles` (module `wiki`), en lecture seule (onglets fixes) hors son action `ordre` (opération `ordonner`) ; sa sous-ressource `entrees` (`regles_onglet_entree`, nom d'affichage dans `lib/libelles-de-la-base.mjs`) reste en lecture seule, bien que la table soit dans `TABLES` : `lib/ressources.mjs#TABLES_SANS_ECRITURE_DIRECTE` (table de `TABLES` sans ressource qui la modifie, avec sa raison ; `ressources-registre` l'exempte). Une page des Règles se crée et se supprime par `pages-du-guide` (entrée de menu comprise), skill `zone-edition-menus`. `personnage_don_obtenu`, une partie de fiche, hors ressource.
- Le tableau « Ressources par module » de `docs/api.md` suit le registre (`test/api-doc.test.mjs`) : une ressource ajoutée ou une capacité changée y est reportée.
- Une dérivée peut avoir sa propre `condition` (même forme que celle d'une ressource) et un `parent` vide : chaque élément en montre alors toutes les lignes qui la satisfont (`serveur/ressources.mjs#lignesDe`). C'est le cas des deux lignes TOTAL du tableau fondu des améliorations d'arme (R167, migration 0081 : `amelioration_total` `arme` et `arme_elementaire`, dans `ameliorations-d-arme` ; `autres-ameliorations` n'a plus que l'armure élémentaire). `types-d-armes-elementaires` est en lecture seule (docs/api.md). Le test du registre tient compte de la condition du lien (`ressources-registre`), `serveur-api-v1` la vérifie.
- Sous-ressource `postures/…/competences-du-critique` (`posture_critique`, R180 ; R182 : la seule valeur de `bonus` est `posture`, Sci du Crit n'y a pas de ligne) : `lib/ressources/regles.mjs` et `docs/api.md`.
- Une colonne figée est refusée en `400` (`colonnesFigees` : `monnaie.nom`, R193).
- Gel (R218, R219 (3) ; skill `zone-edition`) : un `PATCH` ou un `DELETE` d'un mot-clé verrouillé, et tout `POST`, `PATCH` ou `DELETE` d'une monnaie, rendent 409 avec `raisonDuGel`, avant le contrôle des colonnes. `mot_cle.verrou` se lit (`liste`) mais reste en lecture seule (`modifiable: false`) : un corps qui le porte est refusé (400). Le catalogue marque une table de `TABLES_FIGEES` (`figee`) ; OpenAPI décrit ses écritures avec le 409 et sans exemple de corps (`exempleDe` préfère une ligne non gelée).
- Les refus de suppression du service passent tels quels, `details` compris : `DELETE /api/v1/mots-cles/<id>/` d'un mot-clé mentionné rend 409 avec `mentions` et `refus_du_forcage` (R196, `lib/mentions-des-mots-cles.mjs`) ; `DELETE /api/v1/metiers/<id>/` d'un métier dont l'ancre est l'adresse d'un mot-clé rend 409 avec `mots_cles` (skill `zone-edition`). Deux 409 portent `details.mots_cles_verrouilles` : un `DELETE` d'une page visée par l'adresse d'un mot-clé verrouillé (R221, `citations-db.mjs#motsClesVerrouillesQuiYMenent`, `refusDuMotCleVerrouille`), et l'action `fusion` d'un mot-clé cité par la définition d'un verrouillé, cible comprise (R222 (1), `definitionsVerrouilleesQuiCitent`). Test : `serveur-api-v1`.
- Suppression forcée d'un mot-clé (R223, refus et remplacement : skill `zone-mots-cles`) : `DELETE /api/v1/mots-cles/<id>/?forcer=1` (ou `true`), ou le corps `{"forcer":true}` ; `0`, `false` ou l'absence du paramètre : pas de forçage ; une autre valeur, ou `forcer` sur une autre ressource : 400 (`serveur/ressources.mjs#forcageDuDelete`). Les 409 du forçage portent `mots_cles_verrouilles` (définition verrouillée qui cite le mot-clé), `url` et `page` (adresse vers une page de la base) ou `mentions_bloquantes`. Test : `serveur-edition-suppression-forcee`.
- La dernière magie innée d'une race ne se retire pas par `/api/v1/` non plus (400, R210) : ni de `magies-innees-de-l-onglet`, ni de la matrice `acces-aux-magies` (`ressources.mjs` passe par l'opération `magies_innees`). Test : `serveur-api-v1.test.mjs`.
- Le routeur lit le registre : liste paginée (`?q=`, `?tri=`, `?limite=`, `?decalage=`, filtres par colonne), détail avec `ETag`, `POST`, `PATCH` avec `If-Match`, `DELETE`.
- Jamais d'écriture hors de `serveur/edition.mjs#enregistrer` (un lot du journal, skill `zone-edition`). Ce que le service d'édition ne sait pas écrire (colonnes absentes de `TABLES`, pas d'entité dans `ENTITES`, pas d'opération du lot) est en lecture seule : `405` avec `Allow` et la raison, jamais du SQL direct (il serait perdu au rejeu).
- Pour rendre une ressource modifiable, l'apprendre au service d'édition (recette : `docs/api.md`, « Rendre une ressource modifiable ») ; le registre suit (`capacitesDe`).
- Jamais une table des sections 13 et 14 (fiches, comptes, groupes : elles passent par `/api/personnages/` ; journal de l'édition). Jamais une image entière (`ligneSansImage`).
- Le routeur n'injecte un nom de colonne dans le SQL qu'après l'avoir trouvé par `PRAGMA table_info`.
- Les adresses finissent par « / » (skill `zone-service`).
- `OPERATIONS_DU_LOT` (`lib/ressources.mjs`) liste les opérations du lot qu'une ressource peut nommer (`ordonner` comprise) : chacune existe au service et est joignable (`ressources-registre`).
