# Tests : dépôt, sortie du contenu, essai mécanique

Règles générales des tests (état d'import, service, dossiers temporaires) : skill `tests-conventions`.

- **Sortie du contenu** (R296 ; `src/lib/sortie-du-contenu.mjs` : `CONTENU_SORTI = false`, `contenuSorti(env)`, `MAVERICK_CONTENU_SORTI=1` ; migrations mixtes : `MIXTES_SORTIES`, `mixtesSorties()`, `MAVERICK_MIXTES_SORTIES=1`). Allumés par la PR du jour J et la passe S ; éteints, rien ne change.
  - Un test qui ne vaut que tant que ce qui sort est dans le dépôt se déclare par `test/aide-sortie-du-contenu.mjs#testRetireAvecLeContenu(import.meta.url)` (migration de données, registre, `data/rows`, extracteur ; liste `RETIRES_AVEC_LE_CONTENU`) ou `testRetireAvecLesMixtes` (migration mixte elle-même ; liste `RETIRES_AVEC_LES_MIXTES`), avec sa raison (`sortie-du-contenu.test.mjs` vérifie l'accord). Un fichier peut avoir des tests dans les deux listes, un test dans une seule. Seulement si ce qu'il éprouve sort, jamais pour obtenir du vert ; on coupe un test en deux (l'invariant reste, la part qui éprouve la migration sort) plutôt que de le retirer entier.
  - Un registre qui sort et que des tests d'invariants lisent encore se lit par `test/aide-registres-sortis.mjs#registreDeMigration(nom)` (gardé dans `test/fixtures/registres-sortis.json` : ids, clés, balises, cellules, jamais un texte de règle ; il peut n'en garder qu'une partie d'une liste ou des cellules seules), jamais par `data/migrations/<nom>.json` en direct (patron : `guide-sans-chapitres.test.mjs`). `aide-textes-reecrits.mjs#textesReecrits` refuse des fragments `avant`/`apres` manquants. Ce que le code qui tourne lit d'un registre mixte est dans `data/references/` (skill `base-sqlite`).
- **Test de nature « dépôt »** (`db:pages-check`, `db:build` sur `data/rows`, mise à jour ou copie qui écrit `data/rows`) : la CI lance `npm test` sous l'extrait (`MAVERICK_CONTENU`) avec `data/rows` présent, et `client/src/content/wiki` vient alors de l'extrait. Le test retire `MAVERICK_CONTENU` et `MAVERICK_CONTENU_DERIVE` de l'environnement des processus lancés, exporte son wiki depuis `data/rows` dans un dossier temporaire (`db-export-pages --out`) et bâtit sa base par `baseDeDepart(dest, { deriver: true, rows: ROWS })` (patron : `mise-a-jour-paquet.test.mjs`) ; `db-donnees.test.mjs` lance `db-build` sur `data/rows`, sans la variable.
- **Essai mécanique** (`scripts/essai-mecanique-tests.mjs`, `docs/essai-mecanique-des-tests.md`) : chaque fichier de test est lancé seul sur plusieurs contenus, dont la passe C (l'extrait du site de dev, sans `data/rows`) et les variantes V1 à V4.
  - Les variantes sont des saisies fidèles au site (service ou trace `saisie`), sur ce que `edition-modele.mjs` rend modifiable seulement : un test qui casse sur une Vn fige une valeur modifiable. V5 (hors des voies du site) est informative ; la preuve qu'une donnée n'est pas modifiable est un test de refus par `enregistrer` (`serveur-edition-nom-de-magie`).
  - `LIT_LE_DEPOT_PAR_NATURE` ne liste plus que ce qui lit `data/rows` (`db:build`, mise à jour ou copie qui l'écrit, fichier des pages d'exemple), avec sa raison : son échec sur C est attendu tant que `data/rows` est dans le dépôt.
  - Passe D : les fichiers de `LIT_LE_DEPOT_PAR_NATURE` avec `data/rows` ET l'extrait en `MAVERICK_CONTENU`, comme la CI. Un échec y est rouge.
  - Passe S : l'extrait pour contenu dans une copie sans ce qui sortira du dépôt (catégories de `scripts/inventaire-sortie-du-contenu-lib.mjs#listerCeQuiSort` ; `--avec-mixtes` y ajoute les migrations mixtes et pose `MAVERICK_MIXTES_SORTIES=1`), allumée (`environnementDeLaPasse` : `MAVERICK_CONTENU_SORTI=1`, `MAVERICK_SOURCES_RAW` et `MAVERICK_MIGRATIONS_ARCHIVEES` vers des archives `git archive` des exports et des migrations). Aucune rubrique « par nature » : tout échec est rouge. Verte, elle est le critère de fin : `node scripts/essai-mecanique-tests.mjs --passe S [--avec-mixtes] [--controles]`, puis `--trier`.
  - `kit-suffit-au-build.test.mjs` fait un vrai build (~1 min) et tourne dans toutes les passes ; si `node_modules` est un lien, il refait la racine du kit.
  - `--passe <P> --controles` construit le site dans la copie et y lance les tests du site construit (en S, sans `db:build`, qui lit `data/rows`).
- **`data/rows` n'est écrit par aucune PR** (`controle-du-contenu-ecrit`), hors l'export qu'une migration de structure permet (ses tables, `data/rows/VERSION`, les tables qui gardent des noms pour un renommage : `docs/flux-git.md`, « Contenu écrit à la main ») : c'est la copie du site de dev, tenue par « Copier vers le dépôt » et chaque mise à jour (R278). Un contenu qui n'y est pas encore attend la copie du jour.
- **Base remplie.** `client/scripts/base-remplie-lib.mjs` génère une base avec fiches, journal et historique (le contrôle des migrations et `test/aide-structure-sur-place.mjs` l'importent ; `annulerLesMigrations(db)` défait la structure des migrations livrées depuis `NUMERO`, calculé : une migration de structure nouvelle ne demande rien à ces tests). Les migrations livrées à ces tests sont `aide-structure-sur-place.mjs#LIVRAISON` (`lireLesMigrations(LIVRAISON)`, jamais la valeur par défaut : mixtes sorties, `data/schema.sql` est le plancher et la livraison est une copie). `aide-structure-sur-place.mjs#baseDesRegles` vide les tables et colonnes ajoutées depuis `NUMERO` (une table que le site remplit ne fait pas rougir l'essai) et suit les colonnes de `personnage` et `utilisateur`.
- **Base vivante.** `preparerBaseVivante({ garderLeSite: false })` (`serveur/base-vivante.mjs`) est réservé aux tests de la résolution des lots annulés (ancienne forme).
- **Sauvegardes** (`deploy-sauvegardes*.test.mjs`). `test/aide-sauvegardes.mjs` fournit un monde factice, un faux docker et un restic espion ; les tests restic se sautent sans restic, ceux de bash, sqlite3 et flock aussi.
- **Discord** (`deploy-discord`). Sautés sous Windows (`SEUL_LINUX`) ; le test « refus sans rien modifier » y échoue sur l'import du faux docker (`ERR_UNSUPPORTED_ESM_URL_SCHEME`), sans lien avec le code : seule la CI (Linux) les vérifie.
