# Bascule 2, côté hébergement (`deploy/installateur/`)

Éteinte partout : rien de ce que sert la production ne change tant que ses interrupteurs ne sont pas posés. Ce que le jour J change : `docs/chantier-base-de-dev.md`, section 16. Les installateurs, `bascule.sh` et `mise-a-jour.sh` : skill `zone-hebergement` ; l'atelier et le kit : skill `zone-hebergement-atelier`.

## À lire
- `docs/serveur.md`, « Bascule 2 : préparation » (PR 2, 3a, 4, 5a, 5b) ; `deploy/installateur/README.md`, « Activer un kit avec son paquet » ; `docs/flux-git.md`, « Ce que GitHub publie avec la bascule 2 ».
- Côté service : skill `zone-service` (gel, marqueur) ; côté GitHub : skill `zone-mise-a-jour`.

## Invariants
- **Interrupteurs.** Production : le fichier `<production>/activation-par-paquet` (root, jamais un lien) ; absent, `activer.sh` refuse (« éteinte », code 2) avant toute lecture et le fragment de l'installateur (`@@ACTIVATION@@`, absent de l'installateur de test) ne fait rien. Site de dev : `db/bascule-2`. GitHub : `tools/flux-git/bascule-2.json` (skill `zone-mise-a-jour`).
- **Un installateur de production qui n'est pas un « kit seul » reste le modèle**, octet pour octet (test « production = modèle » de `deploy-kit`) : les huit repères `@@SEUL_…@@`, `@@ACTIVATION@@` et `@@VERROU_…@@` sont retirés ou vides. Il ne diffère que par le fragment de l'activation (garde « kit périmé » : `activer.sh` n'est pas lancé si le kit posé n'est pas de la version installée) et la rotation d'`installation.log` (200 Ko, 500 lignes).
- **Le kit seul** (`fabriquer.mjs --kit <racine> --kit-seul`, test et production, sans `--site`) : une archive sans pages. Test : ne pose que `site/_serveur/`, refusé sur une instance sans `atelier/servir`. Production : refus avant toute écriture sans `activation-par-paquet`, hors root, ou hors d'une production installée ; il pose le kit dans `<prod>/activation/kit/` (échec : l'installation est refusée avant l'écriture de `VERSION`, `mise-a-jour.sh` la retente), ne touche ni `site/` ni `site/_serveur/`, puis lance `activer.sh` (`--correctif` pour une étiquette `-hotfix.N` ou `-rebuild.N`). **`VERSION` garde l'étiquette d'avant tant que `activation : == PASSEE` n'est pas dite** : la nouvelle attend dans `activation/version-en-attente`, que la fin de l'installateur, ou `activer.sh` (y compris `--reprendre`) à `PASSEE`, pose ; sinon, marque `.activation-refusee-<tag>` et code de sortie 4.
- **`mise-a-jour.sh`** : pour un installateur « kit seul » de production seulement (`KIT_SEUL=1` ; un installateur complet n'est jamais traité ainsi), le code 3 (pas d'`activation-par-paquet`) pose `.refus-<tag>` et le code 4 (activation non passée) `.activation-refusee-<tag>` : le minuteur ne retente pas, `--force` passe outre, une installation réussie efface les deux marques. Il garde les 3 derniers installateurs (`INSTALLATEURS_GARDES`).
- **Garde-fou 20 d'`activer.sh`** : le service posé vient du kit seul (`activation-conteneur.sh serveur`), jamais du `_serveur/` que la fabrication a laissé ; chaque conteneur (sans réseau, sans capacité, kit et `paquets/` en lecture seule) est supprimé avant que root lise quoi que ce soit, et root ne lit que des fichiers réguliers de 256 Ko au plus, en liste blanche. Le paquet : `stat` (régulier, non lien, 512 Mo au plus) avant toute lecture ; son empreinte est celle du **kit**, seule à faire foi.
- **La bascule courte** : gel 45 min d'abord (`gel.sh poser --duree 45`), service arrêté, copie de la base et de `site/` (`site.precedent/`), pages puis service posés par `poser-un-site.mjs`, santé relue. Un échec ou un signal rend tout (retour automatique) ; `retour_incomplet` dit le geste. `--reprendre` rejoue ; `--correctif` rejoue le dernier paquet (`dernier-paquet.json`). Le rapport (`activation/rapport.json`, copié vers `paquets/activation.json` par `mv -T`) n'a que des raisons d'une liste fermée (`RAISONS_DE_L_ACTIVATION`, un test vérifie que `activer.sh` n'en écrit pas d'autres).
- **`activation-pose.sh`** : crée l'utilisateur système `maverick-site`, lui donne `site/` SAUF `site/_serveur/` (à root) par `find -P … -exec chown -h` (jamais un lien suivi ; un test avec de fausses commandes vérifie les appels).
- **`gel.sh poser|lever|etat`** (POSIX `sh`, root) : livré à la racine des **deux** instances (`FICHIERS_LIVRES`). Écrit `db/gel.json` par fichier provisoire (`mktemp`) puis renommage, en 644. Durée de 1 à 240 min, sinon code 2. Il ne touche ni la base, ni le service, ni `GELER`.
- **`bascule.sh poser-bascule-2` / `retirer-bascule-2`** : `poser` est refusé sans `db/source` ; il ajoute `MAVERICK_DOSSIER_PAQUETS=<prod>/paquets` au `.env` (`retirer` renomme le marqueur et le retire) ; sans eux, `docker-compose.yml` monte `${MAVERICK_DOSSIER_PAQUETS:-/dev/null}:/paquets` en lecture seule, donc rien de réel. Le service ne crée jamais ce dossier.
- **`repetition-bascule-2.sh`** (site de dev, root, `--depuis-la-sauvegarde`, `--garder`) : rejoue sur des copies. Préalable : l'atelier installé et la version installée égale à celle du kit ; il prend le verrou de l'atelier. Étape A (paquet en mode `simulation`, garde-fous 17 et 18, base de la production refaite), étape B (pages dans le conteneur de l'atelier, `CONTENU_FICHIER` et `MODE_REPETITION`). Il n'écrit que des comptes ; code 0 `PASSERAIT`, 1 `REFUSEE`, 2 `IMPOSSIBLE`. `scripts/repetition-bascule-2.mjs` est livré avec le service (`FICHIERS_JOINTS` : il n'importe que des modules livrés).
