# Base SQLite (`data/schema.sql`, `data/rows/`)

## Fichiers
- `data/schema.sql` : la structure. 217 tables STRICT, FTS5, 38 vues, rangées en sections numérotées (en-têtes `-- N. …` du fichier) :
  0 familles d'import ; 1 pages, liens, mots-clés, sources ; 2 règles de la fiche ; 3 magies et sorts ; 4 annexes des magies ; 5 dieux ;
  5 bis chronologie ; 6 classes, spécialités, capacités ; 7 races ; 8 bestiaire (invocations et créatures) ; 8 bis monstres du Bestiaire 2.0 et leurs
  capacités communes ; 9 équipement, ressources, craft, métiers ; 10 notes de cellule et écarts entre sources ; 11 tables dérivées ; 12 vues ;
  13 fiches de personnages et groupes de jeu ; 14 journal de l'édition et brouillon de la note de version ; 15 notes de version et historique des
  modifications du site.
- `data/rows/` : les lignes versionnées, un fichier par table, une instruction `INSERT` par ligne, triées.
- `data/migrations/NNNN-<nom>.sql` (+ registre `.json` pour une migration de données) : tout changement de schéma ou de données (skill `ecrire-une-migration`).
- `client/scripts/db-*.mjs` (build, derive, check, doc, init, export-pages, appliquer-edition, reference), `tools/db/` (`maverick.py`, `migrer.py`, `pages_md.py`, `exporter.py`, `races_onglet.py`, `homonymes.py`).
- Onglet DB : `client/src/lib/donnees.mjs`, `client/src/pages/donnees/` (`index.astro`, `[table].astro`, `maverick.db.ts`).

## À lire
- `docs/sql/remplissage.md` : commandes, qui met quoi à jour, pourquoi `data/rows` est commité, onglet DB, pages fabriquées, `db:migrate`, colonne `remarque`.
- `docs/sql/conception.md` : conventions (`nom`, `titre`, `*_cle`, `origine`, `source_ref`, cascades), §10.1 migrations.
- `docs/sql/structure.md`, `docs/sql/apercu.md` : générés par `npm run db:doc`, jamais écrits à la main.
- Procédures voisines : skill `ecrire-une-migration`, skill `interroger-la-base`, skill `rapatrier-l-edition`, skill `modifier-une-page-wiki`, skill `revue-sql`, skill `relecture-db`.

## Commandes (depuis `client/`)
Détail : `docs/sql/remplissage.md`. `npm run db:build` (→ `var/maverick.db`), `db:check` (code 1), `db:pages-check`, `db:sync-pages` (les `.md` fabriqués → `data/rows`), `db:export-pages` (lancé avant `dev`, `build`, `test`), `db:init`, `db:doc` (régénère `structure.md` et `apercu.md`), `db:migrate`, `db:appliquer-edition -- <journal.json>` (rejoue le journal du site de dev sur `data/rows`, versé dans `historique_modification`, réécrit par `tools/db/exporter.py`).

## Invariants
- `var/maverick.db` est une copie reconstruite, jamais commitée. La seule persistance versionnée est `data/rows`.
- `data/rows` s'écrit tel que l'exporteur l'écrit : jamais de résolution de conflit git à la main (relancer l'importeur ou `db:sync-pages`). Sinon une mise à jour est bloquée (skill `zone-mise-a-jour`).
- Un changement de structure passe par une migration, jamais par une retouche de `data/rows`.
- Les 25 tables de la section 13 (fiches, groupes de jeu) et les 3 de la section 14 (journal de l'édition, brouillon de la note de version)
  restent vides dans `data/rows` ; les vraies fiches vivent dans la base vivante (skill `zone-fiches-base`, skill `zone-service`).
- Journal de l'édition (section 14) : un lot en conflit n'est jamais effacé ni réécrit. Sa résolution (`/mise-a-jour/`, migration 0072) remplit `modification_lot.resolu_le`, `resolution` (JSON) et `resolu_par` (le nouveau lot normal) ; ses lignes restent `conflit` (skill `zone-edition-rejeu`).
- Les commentaires de `data/schema.sql` (recopiés par `db:doc`) ne citent que du code qui existe : fichier cité, `fichier.mjs#Nom`, `#Nom.prop` d'un module de `lib/` (`db-schema.test.mjs`). Un renommage dans le code corrige le commentaire dans le même lot, sans migration (`maverick.py#comparer_schemas` ignore les commentaires), sauf dans le corps d'une `CREATE VIEW` ou `CREATE TRIGGER` : SQLite le garde dans `sqlite_master.sql`, que les tests de migration rejouée (`aide-migration-rejouee.mjs#rejouerLaMigration`) comparent à `data/schema.sql` ; il reste identique à celui de la dernière migration qui crée l'objet, et le changer demande une migration qui le recrée.
- Noms d'affichage : une table ou une colonne nouvelle d'une table que l'édition écrit a son nom français dans `client/src/lib/libelles-de-la-base.mjs` (skill `zone-edition`), sinon `test/libelles-de-la-base.test.mjs` échoue ; une clé normalisée `X_cle` et la provenance n'en demandent pas.
- Identifiants figés : un id ne dérive plus du nom depuis la migration 0006 ; un nom corrigé ou renommé garde son id, une page renommée garde son adresse (skill `base-orthographe`).
- Les lignes typées ne se réimportent pas depuis les classeurs : une mise à jour passe par le rapprochement (skill `sources-rapprochement`).
- Colonne `remarque` : chaque table d'entités en a une, texte libre, vide par défaut, qui reprend les notes de cellule des classeurs (réunies, séparées par une ligne vide). `note_cellule` n'est qu'une trace : le site lit la remarque. `db:check` vérifie qu'aucune note n'est absente de la remarque de sa ligne.
- Provenance (`famille`, `origine`, `source_ref`) : retirée à la 1.0 (`CLAUDE.md`) ; n'y rien investir.
- Page retirée, identifiants figés (migrations 0094, 0095 ; registre `0005-orthographe-base.json`) : les ids `guide/postures#posture:…` gardent leur préfixe, leurs `page_entite` sont rattachées à `guide/les-postures` ; les 3 textes de `mode_texte` gardent `guide/liste-des-effets-mode-hyper#texte:…`, rattachés à `guide/le-mode-hyper` comme les 12 constantes `mode_hyper.*` et `mode_hyper_100.*` (le CHECK de `mode_texte` n'admet que cette exception d'id). Pour une sous-entité dont la page d'origine est retirée, `db:check` prend la colonne `page_id` de la table.
- Améliorations d'arme (R167, migration 0081) : un seul tableau pour l'arme du catalogue et l'arme élémentaire. Les lignes de cible `arme` portent le coût matériel (`cout_brut`…) et le coût élémentaire (`cout_elementaire_brut`, `cout_gemmes`…) ; la cible `arme_elementaire` ne reste que dans `amelioration_total`. Type d'une famille : `arme_famille.type_elementaire_id` (NULL pour ARME DE MONSTRES et une famille créée sur le site de dev, R159 ; le site ne le modifie pas) ; `arme_elementaire_type` et ses `_competence` et `_degats` (types posés par la décision, jamais recalculés depuis `arme_degats` ; la bombe, `type_degats_au_choix` = 1, a son choix dans `personnage_arme.type_degats_choisi`).
- Mots-clés (migrations 0113 à 0116, R232, R233, R235 ; règles : skill `zone-mots-cles`) : `mot_cle.id` entier, figé, jamais réutilisé ; `mot_cle.cle`, calculée, dont `db:check` vérifie la règle (`clesDesMotsCles`) ; `monnaie_id` (`ON DELETE SET NULL`) ; `icone` (0116 : `<famille>:<id>`, comparée à `lib/icones.mjs` par `db:check`) ; `page_tag.tag_id` et `sort_mot_cle.mot_cle_id` entiers. Tables `categorie_mot_cle`, `mot_cle_categorie`, `mot_cle_ancienne_cle`, `mot_cle_synonyme` (remplace `mot_cle.abreviation`, R183, 0090 ; 0115, R233 (7)). Le registre `.json` de la 0113 (ancien id texte → id entier) est figé et sert au rejeu (skill `zone-edition-rejeu`). « CR » est un synonyme de `corruption`. `couleur` et `url` (0098) : skill `zone-mots-cles-liens`.
- Verrou des mots-clés (R218, R219, migration 0110) : `mot_cle.verrou` vaut 0 ou 1 (`NOT NULL DEFAULT 0`, CHECK) et ne change que par migration ; qui l'a, et ce qu'il refuse : skill `zone-mots-cles-service`.
- Dérivées (`scripts/db-derive.mjs`) : `lien` (vue `lien_page`) = les `[[…]]` (pages d'exemple), puis chaque balise d'un mot-clé dont l'adresse mène à une page (`adresses-db.mjs#pageDeLAdresse`) ; `page_fts` indexe le texte affiché (`texteSansBalises`), jamais l'id d'un mot-clé.
- Plan des Règles (R184, R185, migration 0091), section 1 : `regles_onglet` (`ouverture_page_id`) et `regles_onglet_entree` (le menu latéral). L'ouverture d'un onglet est une clé étrangère composée différée vers une entrée de cet onglet : onglet et entrées s'écrivent dans une même transaction. `rang` et `ordre` sans UNIQUE (échange de deux places dans un lot ; l'id départage). `page_id` UNIQUE ON DELETE CASCADE. Lu par `lib/plan-des-regles-db.mjs` (skill `zone-guide`), hors des listes de `lib/tables-de-la-base.mjs`. L'édition modifie les entrées, jamais `regles_onglet` (skill `zone-edition-menus`).
- Ordre des races (migration 0092) : `race.rang_liste` donne l'ordre du menu latéral des races, de `/races/` et du tableau des magies innées. Nullable (NULL en fin de liste, par nom), sans UNIQUE, distinct de `race.ordre` (onglet « Race » et fiche : skill `zone-races`). Une race créée prend le rang suivant.
- Compteurs d'usage (R173, 0085) : `personnage_action_usage`, ligne absente = au maximum.
- Réussite critique (R180, 0087 ; R182, 0089) : `regle_constante` `critique.*` ; `posture_critique.bonus` n'admet que `'posture'` (Sci du Crit : mentionné, jamais compté). `personnage_sort.prepare_critique` (plage figée du sort préparé) : CHECK écrit de 1 (bas de « 1 à N », R180, R54) à 15 (le test le compare à `critique.plafond`). Sa borne basse est `critique.plancher` (R203, 0101) ; le CHECK ne change pas.
- Migrations de données R198 à R210 et R224 à R231 : chacune a son registre `.json` et n'écrit rien dans `historique_modification`. Les registres de 0104, 0105, 0107, 0108, 0111 et 0112 écrivent `textes`, jamais `corrections`, que `tools/sources/rapprocher.mjs` lit comme de l'orthographe (skill `sources-rapprochement`) :
  - 0103 (R205) : l'état s'écrit « Gel » dans les textes de règles ; registre `0103-r205-etat-gel.json`.
  - 0104 et 0107 : mots-clés `maroquinier` et `armurier` ; `attaque-gratuite` garde son identifiant et renvoie par sa définition, sans adresse.
  - 0105, 0108, 0109 (E6, R207) : constante `constante_equipement` `armure.unites_par_materiau`.
  - 0111 (R224 à R230) : les copies sont corrigées là où elles contredisent une décision (R224 (1)). La règle `gains_sante_potentiel` de `v_personnage_controle` (R225) lit `regle_constante` `potentiel_illimite.sante_max_par_niveau`. Le mot-clé `mode-super` mène à `/regles/mode-super/` (R228) ; `reussites-echecs-et-critiques` est créé ; un mot-clé à adresse posé par une migration est verrouillé et sa garde exige `url IS NULL`. Une migration qui change un texte de `metier` change `artisanat_texte`, `artisanat_brut` (recalculé) et le corps de la page, égal à `corpsDeMetier(ligne)` (R230 (1)).
  - 0112 (R231) : réécriture de `guide/attaquer-et-se-defendre` et `guide/attaque-et-defense` ; fixture `client/test/fixtures/lots-avant-0112.json` (`db-r231-attaquer-et-se-defendre.test.mjs`).
- Tableau libre du Mage Bleu (R181, migration 0088) : `classe_annexe_entree`, une ligne par « (Type) Nom. Effet » d'une ligne de `classe_annexe` (54 entrées), id figé `classes/mage-bleu#entree:<magie>:<nom>`, texte cité tel quel (joint dans l'ordre de `rang` = le texte de la ligne). `capacite_variable` : la magie (`innee` ou `acquise`) que vise un don « Variable », une donnée, jamais lue par le nom du don ; le site de dev l'écrit (création, changement de type ou de magie : skill `zone-edition`). Les règles d'un don partent avec lui (skill `zone-edition`). Choix des fiches : skill `zone-fiches-base`.
- Spécialisations magiques (R236, R237, R243 à R246, migration 0117, test `db-0117-magies-v10-specialisations.test.mjs`) : table `magie_specialisation`, id figé `<magie.id>#specialisation:<slug>`, `ordre` 1 ou 2 (28 lignes, aucune pour le Potentiel Illimité) ; `sort.specialisation_id`, son CHECK de préfixe (une spécialisation de la magie du sort) et `niveau >= 3`. `sort.ordre` va de 1 à 30 par magie : 1 à 10 le tableau commun (NPM 1 et 2), 11 à 20 la spécialisation 1, 21 à 30 la spécialisation 2 (NPM 3 à 5). - Classes de Décembre (R238, R241, R252, migration 0119, test `db-0119-classes-materiaux-d12.test.mjs`) : 41 classes, 694 capacités ; la règle `classe_imposee` quitte `v_personnage_controle` (`classe_reservee` et `classe_exclue` restent). ## Choix du propriétaire
- Le site tire de la base toutes ses pages et l'onglet **DB** : `/donnees/` (tables et vues) et la base en téléchargement `/donnees/maverick.db` (absente de la version portable).
- Le Potentiel Illimité n'a ni gemme, ni bois, ni bâton magique, ni pièce élémentaire (décision R160) : la base le refuse. `gemme`, `bois`,
  `baton_magique`, `arme_elementaire` et `armure_elementaire` portent la contrainte nommée `<table>_sans_potentiel_illimite`
  (`CHECK (magie_id <> 'magies/potentiel-illimite')`, migration 0078) ; une migration ou une édition qui en ajoute une échoue. Une table reconstruite garde cette contrainte.
