# Base SQLite (`data/schema.sql`, `data/rows/`)

## Fichiers
- `data/schema.sql` : la structure. 212 tables STRICT, FTS5, 38 vues, rangées en sections numérotées (en-têtes `-- N. …` du fichier) :
  0 familles d'import ; 1 pages, liens, mots-clés, sources ; 2 règles de la fiche ; 3 magies et sorts ; 4 annexes des magies ; 5 dieux ;
  5 bis chronologie ; 6 classes, spécialités, capacités ; 7 races ; 8 bestiaire (invocations et créatures) ; 8 bis monstres du Bestiaire 2.0 et leurs
  capacités communes ; 9 équipement, ressources, craft, métiers ; 10 notes de cellule et écarts entre sources ; 11 tables dérivées ; 12 vues ;
  13 fiches de personnages et groupes de jeu ; 14 journal de l'édition et brouillon de la note de version ; 15 notes de version et historique des
  modifications du site.
- `data/rows/` : les lignes versionnées, un fichier par table, une instruction `INSERT` par ligne, triées.
- `data/migrations/NNNN-<nom>.sql` (+ registre `.json` pour une migration de données) : tout changement de schéma ou de données (skill `ecrire-une-migration`).
- `client/scripts/db-*.mjs` (build, derive, check, doc, init, export-pages, appliquer-edition, reference), `tools/db/` (`maverick.py`, `migrer.py`, `pages_md.py`, `exporter.py`, `races_onglet.py`, `homonymes.py`).
- Onglet DB : `client/src/lib/donnees.mjs`, `client/src/pages/donnees/` (`index.astro`, `[table].astro`, `maverick.db.ts`).

## À lire
- `docs/sql/remplissage.md` : commandes, qui met quoi à jour, pourquoi `data/rows` est commité, onglet DB, pages fabriquées, `db:migrate`, colonne `remarque`.
- `docs/sql/conception.md` : conventions (`nom`, `titre`, `*_cle`, `origine`, `source_ref`, cascades), §10.1 migrations.
- `docs/sql/structure.md`, `docs/sql/apercu.md` : générés par `npm run db:doc`, jamais écrits à la main.
- Procédures voisines : skill `ecrire-une-migration`, skill `interroger-la-base`, skill `rapatrier-l-edition`, skill `modifier-une-page-wiki`, skill `revue-sql`, skill `relecture-db`.

## Commandes (depuis `client/`)
Détail : `docs/sql/remplissage.md`. `npm run db:build` (→ `var/maverick.db`), `db:check` (code 1), `db:pages-check`, `db:sync-pages` (les `.md` fabriqués → `data/rows`), `db:export-pages` (lancé avant `dev`, `build`, `test`), `db:init`, `db:doc` (régénère `structure.md` et `apercu.md`), `db:migrate`, `db:appliquer-edition -- <journal.json>` (rejoue le journal du site de dev sur `data/rows`, versé dans `historique_modification`, réécrit par `tools/db/exporter.py`).

## Invariants
- `var/maverick.db` est une copie reconstruite, jamais commitée. La seule persistance versionnée est `data/rows`.
- `data/rows` s'écrit tel que l'exporteur l'écrit : jamais de résolution de conflit git à la main (relancer l'importeur ou `db:sync-pages`). Sinon une mise à jour est bloquée (skill `zone-mise-a-jour`).
- Un changement de structure passe par une migration, jamais par une retouche de `data/rows`.
- Les 24 tables de la section 13 (fiches, groupes de jeu) et les 3 de la section 14 (journal de l'édition, brouillon de la note de version)
  restent vides dans `data/rows` ; les vraies fiches vivent dans la base vivante du service (skill `zone-fiches-base`, skill `zone-service`).
- Journal de l'édition (section 14) : un lot en conflit n'est jamais effacé ni réécrit. Sa résolution (`/mise-a-jour/`, migration 0072) remplit
  `modification_lot.resolu_le`, `resolution` (les choix, JSON) et `resolu_par` (le nouveau lot normal, jamais lui-même) ; ses lignes restent
  `conflit`, avec leur `detail` (skill `zone-edition-rejeu`).
- Les commentaires de `data/schema.sql` (recopiés par `db:doc`) ne citent que du code qui existe : un fichier `.mjs`, `.astro`,
  `.css` cité existe, un renvoi `fichier.mjs#Nom` nomme une définition du fichier, et `#Nom.prop` une propriété de l'export d'un module de `lib/`
  (`db-schema.test.mjs`). Un renommage dans le code corrige le commentaire dans le même lot, sans migration (`comparer_schemas` ignore les commentaires), sauf dans le corps d'une `CREATE VIEW` ou `CREATE TRIGGER` : SQLite garde ce corps entier dans `sqlite_master.sql` et les tests de migration rejouée (`aide-migration-rejouee.mjs#rejouerLaMigration`) le comparent à `data/schema.sql`. Un commentaire de ce corps reste identique, au caractère près, à celui de la dernière migration qui crée l'objet ; le changer demande une migration qui recrée l'objet.
- Noms d'affichage : une table ou une colonne nouvelle d'une table que l'édition écrit a son nom français dans `client/src/lib/libelles-de-la-base.mjs` (skill `zone-edition`), sinon `test/libelles-de-la-base.test.mjs` échoue ; une clé normalisée `X_cle` et la provenance n'en demandent pas.
- Identifiants figés : un id ne dérive plus du nom depuis la migration 0006 ; un nom corrigé ou renommé garde son id, une page renommée garde son adresse
  (skill `base-orthographe`).
- Les lignes typées ne se réimportent pas depuis les classeurs : une mise à jour passe par le rapprochement (skill `sources-rapprochement`).
- Colonne `remarque` : chaque table d'entités en a une, texte libre, vide par défaut, qui reprend les notes de cellule des classeurs (réunies, séparées par une ligne vide). `note_cellule` n'est qu'une trace : le site lit la remarque. `db:check` vérifie qu'aucune note n'est absente de la remarque de sa ligne.
- Provenance (`famille`, `origine`, `source_ref`) : retirée à la 1.0 (`CLAUDE.md`) ; n'y rien investir.
- Page retirée, identifiants figés (migrations 0094, 0095 ; registre `0005-orthographe-base.json`) : les ids `guide/postures#posture:…` gardent leur préfixe, leurs lignes `page_entite` sont rattachées à `guide/les-postures` ; les 3 textes du Mode Hyper de `mode_texte` gardent `guide/liste-des-effets-mode-hyper#texte:…` et sont rattachés à `guide/le-mode-hyper`, comme les 12 constantes `mode_hyper.*` et `mode_hyper_100.*`. Le CHECK de `mode_texte` n'admet que cette exception d'id. Pour une sous-entité dont la page d'origine est retirée, `db:check` prend la colonne `page_id` de la table.
- Améliorations d'arme (R167, migration 0081) : un seul tableau pour l'arme du catalogue et l'arme élémentaire. Les lignes de cible `arme` portent le coût matériel (`cout_brut`…) et le coût élémentaire (`cout_elementaire_brut`, `cout_gemmes`…) ; la cible `arme_elementaire` ne reste que dans `amelioration_total`. Type d'une famille : `arme_famille.type_elementaire_id` (NULL pour ARME DE MONSTRES et pour une famille créée sur le site de dev, R159 : aucune arme élémentaire ; le site ne le modifie pas) ; `arme_elementaire_type` et ses `_competence` et `_degats` (types physiques posés par la décision, jamais recalculés depuis `arme_degats` ; sauf la bombe, `type_degats_au_choix` = 1, dont le choix est `personnage_arme.type_degats_choisi`). Solidité de base : `constante_equipement` `piece_elementaire.solidite_base` (migration 0080) + `bonus_cran` de la ligne d'amélioration.
- Mots-clés (R183, migration 0090) : `mot_cle.abreviation`, au plus une par mot-clé, NULL sinon ; `db:check` en contrôle l'unicité et l'absence d'ambiguïté (`fautesDeLAbreviation` : skill `zone-mots-cles`). L'id `cr` n'existe plus (CR est l'abréviation de `corruption`) ; la page `guide/lexique` est retirée. `couleur` et `url` (0098) : skill `zone-mots-cles-liens`.
- Verrou des mots-clés (R218, R219, migration 0110) : `mot_cle.verrou` vaut 0 ou 1 (`NOT NULL DEFAULT 0`, CHECK). Il vaut 1 pour les mots-clés à adresse, `rf`, `ro`, `pp`, ceux de `MOTS_CLES_PROTEGES` et ceux d'une race, d'une magie ou d'une classe ; une création vaut 0, sauf `race-hybride` (R220 (2)). Il ne change que par migration : aucune route du site ne l'écrit (skill `zone-mots-cles`).
- Dérivées (`scripts/db-derive.mjs`) : `lien` (vue `lien_page`) = les `[[…]]` (pages d'exemple), puis chaque balise d'un mot-clé dont l'adresse mène à une page (`adresses-db.mjs#pageDeLAdresse`) ; `page_fts` indexe le texte affiché (`texteSansBalises`), jamais l'id d'un mot-clé.
- Plan des Règles (R184, R185, migration 0091), section 1 : `regles_onglet` (id, titre, `ordre`, `ouverture_page_id`) et `regles_onglet_entree` (le menu latéral). L'ouverture d'un onglet est une clé étrangère composée différée vers une entrée de cet onglet : onglet et entrées s'écrivent dans une même transaction. `rang` (et `ordre`) sans UNIQUE, pour échanger deux places dans un même lot : à égalité, l'id départage. Ids `page:<id>`, `lien:<adresse>`, `bientot:<clé>` ; `page_id` UNIQUE ON DELETE CASCADE. Lu par `lib/plan-des-regles-db.mjs` (skill `zone-guide`), hors des listes de `lib/tables-de-la-base.mjs`. L'édition modifie les entrées, jamais `regles_onglet` (ordre, titre, ouverture fixes : skill `zone-edition-menus`).
- Ordre des races (migration 0092) : `race.rang_liste` donne l'ordre du menu latéral des races, de `/races/` et du tableau des magies innées. Nullable (NULL en fin de liste, par nom), sans UNIQUE (un réordonnancement renumérote plusieurs races d'un lot), distinct de `race.ordre` (onglet « Race » et fiche : skill `zone-races`). Une race créée prend le rang suivant.
- Compteurs d'usage (R173, 0085) : `personnage_action_usage`, ligne absente = au maximum.
- Réussite critique (R180, 0087 ; R182, 0089) : `regle_constante` `critique.*` ; `posture_critique.bonus` n'admet que `'posture'` (Sci du Crit : mentionné, jamais compté). `personnage_sort.prepare_critique` (plage figée du sort préparé) : CHECK écrit de 1 (bas de « 1 à N », R180, R54) à 15 (le test le compare à `critique.plafond`). Sa borne basse est `critique.plancher` (R203, 0101) ; le CHECK ne change pas.
- Migrations de données R198 à R210, R224 à R229 et R231, chacune avec son registre `.json` et rien dans `historique_modification` :
  - 0101 : `regle_constante` `critique.plancher` (R203). 0102 : description de Calme (R204).
  - 0103 : l'état s'écrit « Gel » dans les textes de règles (R205), registre `0103-r205-etat-gel.json`.
  - 0104 et 0107 : textes de R198 à R208 (pages du guide, définitions de mots-clés) et mots-clés `maroquinier` et `armurier` ; `attaque-gratuite` garde son identifiant et renvoie par sa définition, sans adresse.
  - 0105, 0108 et 0109 : E6 (R207), armures de la grille et boucliers calculés, 42 recettes de bâton, panneau Armes, bloc du panneau Bâtons magiques (R207 (3), registre `textes`) ; constante `constante_equipement` `armure.unites_par_materiau`.
  - 0106 : bestiaire (R209).
  - 0111 : relecture des Règles contre les décisions (C1 à C26, R224 à R230). Les copies sont corrigées là où elles contredisent une décision (R224 (1)). Registre : `textes` (avec `correction` et `decision`), `titres`, `alias`, `mots_cles_crees`, `mots_cles`, `constantes`. La règle `gains_sante_potentiel` de `v_personnage_controle` (R225) lit `regle_constante` `potentiel_illimite.sante_max_par_niveau`. Le mot-clé `mode-super` mène à `/regles/mode-super/` (R228) ; `reussites-echecs-et-critiques` est créé. Un mot-clé à adresse posé par une migration est verrouillé, et sa garde exige `url IS NULL`. C26 touche aussi `metier` (R230 (1)). Invariant : une migration qui change un texte de `metier` change `artisanat_texte`, `artisanat_brut` (recalculé depuis lui) et le corps de la page, égal à `corpsDeMetier(ligne)` (le Bijoutier).
  - 0112 (R231) : réécriture entière de `guide/attaquer-et-se-defendre` et `guide/attaque-et-defense` et mots-clés de la fiche ; registre `textes` (valeur entière) et `renvois` ; fixture `client/test/fixtures/lots-avant-0112.json` (`db-r231-attaquer-et-se-defendre.test.mjs`).
  - Les registres de 0104, 0105, 0107, 0108, 0111 et 0112 écrivent `textes`, jamais `corrections`, que `tools/sources/rapprocher.mjs` lit comme de l'orthographe (skill `sources-rapprochement`).
- Tableau libre du Mage Bleu (R181, migration 0088) : `classe_annexe_entree`, une ligne par « (Type) Nom. Effet » d'une ligne de `classe_annexe` (54 entrées), id figé `classes/mage-bleu#entree:<magie>:<nom>`, texte cité tel quel (joint dans l'ordre de `rang` = le texte de la ligne). `capacite_variable` : la magie (`innee` ou `acquise`) que vise un don « Variable », une donnée, jamais lue par le nom du don ; le site de dev l'écrit (création, changement de type ou de magie : skill `zone-edition`). Les règles d'un don partent avec lui (skill `zone-edition`). Choix des fiches : skill `zone-fiches-base`.
- Plafonds de NPM (R188, migration 0097) : `magie_npm_plafond` (`magies/potentiel-illimite` → 3) et `capacite_npm_plafond` (`capacites/archimage-semi-complet` → 4). Effet seulement si la magie innée a un plafond ; effectif = max(magie, dons acquis), au plus la table des niveaux (R16) ; ne borne que le choix des sorts. `capacite_condition_emplacements` (R189) : lue par le moteur seul. Valeurs jamais lues dans un texte.
- Migration 0099 : `v_arme.solidite_sans_composition` applique le plancher de R51 (au moins 1), simple sécurité (R194) ; `invocation.tableau_sort_id` (clé étrangère nullable vers `sort`) désigne le sort dont le tableau est celui de l'invocation (skill `zone-bestiaire`). Migration 0100 : ancres figées `{#ancre}` des 20 états de `guide/liste-des-alterations-d-etat` et des 2 sections de la ceinture (skills `zone-magies`, `zone-ceinture`).
- Résistances physiques (R174, migration 0083) : `magie_resistance.cible_type` admet `'physique'`, avec `cible_physique` (`estoc`, `taille`, `frappe`) ; la contrainte nommée `magie_resistance_une_cible` veut exactement une cible renseignée, celle de `cible_type`. Seules lignes physiques : les trois vulnérabilités du Potentiel Illimité. Leur annulation en Mode Hyper (R172) n'est pas une donnée de la table.
- Le site de dev est la source de ce qu'il modifie : une valeur de l'import se lit par `client/src/lib/historique-site.mjs` (`valeurDImport`, `lignesDImport`,
  `effectifDImport`, table `historique_modification`).

## Choix du propriétaire
- Le site tire de la base toutes ses pages (`.md` fabriqués au build) et l'onglet **DB** : `/donnees/` (tables et vues) et la base en
  téléchargement `/donnees/maverick.db` (absente de la version portable).
- Le Potentiel Illimité n'a ni gemme, ni bois, ni bâton magique, ni pièce élémentaire (décision R160) : la base le refuse. `gemme`, `bois`,
  `baton_magique`, `arme_elementaire` et `armure_elementaire` portent la contrainte nommée `<table>_sans_potentiel_illimite`
  (`CHECK (magie_id <> 'magies/potentiel-illimite')`, migration 0078) ; une migration ou une édition qui en ajoute une échoue (`bois` : `bois_sans_potentiel_illimite`). Une table reconstruite
  garde cette contrainte.
