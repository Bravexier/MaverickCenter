# Base SQLite : ce que les migrations ont fixé

Noyau (fichiers, commandes, invariants communs) : skill `base-sqlite`. Écrire une migration : skill `ecrire-une-migration`. Le détail est dans le registre `.json` et le test de chaque migration.

## Invariants
- Page retirée, identifiants figés (migrations 0094, 0095 ; registre `0005-orthographe-base.json`) : les ids `guide/postures#posture:…` gardent leur préfixe, leurs `page_entite` rattachées à `guide/les-postures` ; les 3 textes de `mode_texte` gardent `guide/liste-des-effets-mode-hyper#texte:…`, rattachés à `guide/le-mode-hyper` comme les constantes `mode_hyper.*` et `mode_hyper_100.*` (le CHECK de `mode_texte` n'admet que cette exception d'id). Pour une sous-entité dont la page d'origine est retirée, `db:check` prend la colonne `page_id` de la table.
- Améliorations d'arme (R167, migration 0081) : un seul tableau pour l'arme du catalogue et l'arme élémentaire. Les lignes de cible `arme` portent le coût matériel (`cout_brut`…) et le coût élémentaire (`cout_elementaire_brut`, `cout_gemmes`…) ; la cible `arme_elementaire` ne reste que dans `amelioration_total`. Type d'une famille : `arme_famille.type_elementaire_id` (NULL pour ARME DE MONSTRES et une famille créée sur le site de dev, R159 ; le site ne le modifie pas) ; `arme_elementaire_type` et ses `_competence` et `_degats` (types posés par la décision, jamais recalculés depuis `arme_degats` ; la bombe, `type_degats_au_choix` = 1, a son choix dans `personnage_arme.type_degats_choisi`).
- Mots-clés (migrations 0113 à 0116, R232, R233, R235 ; règles : skill `zone-mots-cles`) : `mot_cle.id` entier, figé, jamais réutilisé ; `mot_cle.cle`, calculée, dont `db:check` vérifie la règle (`clesDesMotsCles`) ; `monnaie_id` (`ON DELETE SET NULL`) ; `icone` (0116 : `<famille>:<id>`, comparée à `lib/icones.mjs` par `db:check`) ; `page_tag.tag_id` et `sort_mot_cle.mot_cle_id` entiers. Tables `categorie_mot_cle`, `mot_cle_categorie`, `mot_cle_ancienne_cle`, `mot_cle_synonyme` (remplace `mot_cle.abreviation`, R183, 0090 ; 0115, R233 (7)). Le registre `.json` de la 0113 (ancien id texte → id entier) est figé et sert au rejeu (skill `zone-edition-rejeu`). `couleur` et `url` : skill `zone-mots-cles-liens`.
- Verrou des mots-clés (R218, R219, migration 0110) : `mot_cle.verrou` vaut 0 ou 1 (`NOT NULL DEFAULT 0`, CHECK) et ne change que par migration ; qui l'a, et ce qu'il refuse : skill `zone-mots-cles-service`.
- Plan des Règles (R184, R185, migration 0091), section 1 : `regles_onglet` (`ouverture_page_id`) et `regles_onglet_entree` (le menu latéral). L'ouverture d'un onglet est une clé étrangère composée différée vers une entrée de cet onglet : onglet et entrées s'écrivent dans une même transaction. `rang` et `ordre` sans UNIQUE (échange de deux places dans un lot ; l'id départage) ; `rang` n'est pas continu : une page retirée, par migration (0122) ou par le site (`serveur/edition-plan.mjs:199`), laisse son rang libre, sans renumérotation. `page_id` UNIQUE ON DELETE CASCADE. Lu par `lib/plan-des-regles-db.mjs` (skill `zone-guide`), hors des listes de `lib/tables-de-la-base.mjs`. L'édition modifie les entrées, jamais `regles_onglet` (skill `zone-edition-menus`). Depuis la 0122, l'onglet Exploration s'ouvre sur `guide/equipement-et-butin`. Une page en doublon se retire en fondant son mot-clé dans celui de la page gardée, comme une fusion du site (0122 : 172 → 138 ; `{{x}}` → `{{cible|libellé de x}}`, la clé de x en clé quittée de la cible, ses catégories retirées), avec son entrée dans `serveur/edition.mjs#FUSIONS_DE_MIGRATION` : un lot du journal en attente se rejoue sans conflit, et jamais deux mots-clés ne mènent à la même adresse. Les tests des migrations antérieures lisent la page et le mot-clé retirés dans le registre (`test/aide-migration-0122.mjs`, `test/aide-migration-0124.mjs`).
  - 0124 (R272) : `guide/fiche-accessoires-et-ceinture` est fondue dans `guide/fiche-inventaire-sac-a-dos` sous les ancres figées `{#accessoires}` et `{#ceinture}` ; le mot-clé 136 est fondu dans le 139, qui mène à `/regles/inventaire-sac-a-dos/` (id et slug inchangés) ; la constante R89 `ceinture.exemplaires_par_emplacement` suit la page ; `FUSIONS_DE_MIGRATION` a son entrée 0124. Les tests qui rejouent la 0100 ignorent `PAGE_DE_REFERENCE` (sa page d'origine n'existe plus).
- Ordre des races (migration 0092) : `race.rang_liste` donne l'ordre du menu latéral des races, de `/races/` et du tableau des magies innées. Nullable (NULL en fin de liste, par nom), sans UNIQUE, distinct de `race.ordre` (onglet « Race » et fiche : skill `zone-races`). Une race créée prend le rang suivant.
- Races Fongoïde et Gémidien (R239, R256, migration 0120 ; test `db-0120-races-fongoide-gemidien.test.mjs`) : `race.ordre` recule de deux (en deux temps : UNIQUE) et `rang_liste` va de 1 à 29 ; leur Mode Hyper est `mode_hyper_effet` version `onglet_race` ; les colonnes de la fiche V15.2.2 de `race` valent NULL (la fiche n'a pas ces races). `pages_md.py#origine_migration` accepte la provenance « Nouveauté mise à jour Décembre » (famille des pages de leur type). Leurs mots-clés 408 et 409 ne sont pas verrouillés (R219 (5) : un mot-clé créé plus tard ne l'est pas, même pour une nouvelle race).
- Compteurs d'usage (R173, 0085) : `personnage_action_usage`, ligne absente = au maximum.
- Réussite critique (R180, 0087 ; R182, 0089) : `regle_constante` `critique.*` ; `posture_critique.bonus` n'admet que `'posture'` (Sci du Crit : mentionné, jamais compté). `personnage_sort.prepare_critique` (plage figée du sort préparé) : CHECK écrit de 1 (bas de « 1 à N », R180, R54) à 15. Sa borne basse est `critique.plancher` (R203, 0101) ; le CHECK ne change pas.
- Migrations de données R198 à R210 et R224 à R231 : chacune a son registre `.json` et n'écrit rien dans `historique_modification`.
  - 0103 (R205) : l'état s'écrit « Gel » dans les textes de règles ; registre `0103-r205-etat-gel.json`.
  - 0104 et 0107 : mots-clés `maroquinier` et `armurier` ; `attaque-gratuite` garde son identifiant et renvoie par sa définition, sans adresse.
  - 0105, 0108, 0109 (E6, R207) : constante `constante_equipement` `armure.unites_par_materiau`.
  - 0111 (R224 à R230) : les copies sont corrigées là où elles contredisent une décision (R224 (1)). La règle `gains_sante_potentiel` de `v_personnage_controle` (R225) lit `regle_constante` `potentiel_illimite.sante_max_par_niveau`. Le mot-clé `mode-super` mène à `/regles/mode-super/` (R228) ; `reussites-echecs-et-critiques` est créé ; un mot-clé à adresse posé par une migration est verrouillé et sa garde exige `url IS NULL`. Un texte de `metier` changé par migration change aussi `artisanat_texte`, `artisanat_brut` (recalculé) et le corps de la page, égal à `corpsDeMetier(ligne)` (R230 (1)).
  - 0112 (R231) : réécriture de `guide/attaquer-et-se-defendre` et `guide/attaque-et-defense` ; fixture `client/test/fixtures/lots-avant-0112.json` (`db-r231-attaquer-et-se-defendre.test.mjs`).
- Tableau libre du Mage Bleu (R181, migration 0088) : `classe_annexe_entree`, une ligne par « (Type) Nom. Effet » d'une ligne de `classe_annexe` (54 entrées), id figé `classes/mage-bleu#entree:<magie>:<nom>`, texte cité tel quel (joint dans l'ordre de `rang` = le texte de la ligne). `capacite_variable` : la magie (`innee` ou `acquise`) que vise un don « Variable », une donnée, jamais lue par le nom du don ; le site de dev l'écrit (création, changement de type ou de magie : skill `zone-edition`). Les règles d'un don partent avec lui (skill `zone-edition`). Choix des fiches : skill `zone-fiches-base`.
- Spécialisations magiques (R236, R237, R243 à R246, migration 0117, test `db-0117-magies-v10-specialisations.test.mjs`) : table `magie_specialisation`, id figé `<magie.id>#specialisation:<slug>`, `ordre` 1 ou 2 (aucune pour le Potentiel Illimité) ; `sort.specialisation_id`, son CHECK de préfixe (une spécialisation de la magie du sort) et `niveau >= 3`. `sort.ordre` va de 1 à 30 par magie : 1 à 10 le tableau commun (NPM 1 et 2), 11 à 20 la spécialisation 1, 21 à 30 la spécialisation 2 (NPM 3 à 5). Le CHECK ne dit qu'un sens ; `db:check` dit l'autre : un sort de NPM 3 à 5 a une spécialisation hors Potentiel Illimité ; chaque magie en a 2, le Potentiel Illimité 0. `amelioration_cadaverique` n'existe plus (R237 (7)) ; `magie_role` est vide.
  - Coûts (R244) : le chakra va dans `cout_brut`, le reste dans `cout_secondaire`, lus comme la 0065 (R106) ; `db:check` exige `cout_chakra = analyserCout(cout_brut, cout_secondaire)`. Projectile arcanique (R251, migration 0118) : `cout_brut` « 4/projectile », `cout_chakra` 4, le progressif (+K par projectile) est calculé par la fiche (skill `zone-fiche-sorts`).
  - Choix de la fiche (R236, migration 0118, test `db-0118-specialisation-de-la-fiche.test.mjs`) : `personnage_specialisation_magie (personnage_id, magie_id, specialisation_id)`, PK (`personnage_id`, `magie_id`), clé étrangère composée vers `magie_specialisation (id, magie_id)`. Deux règles de `v_personnage_controle`, pour le bi-magie seul : `sort_hors_specialisation`, `specialisation_hors_magie` (skill `zone-fiches-base`).
  - Poupée fulgurante (R246) : créature d'invocation, donc le registre `tools/sources/ignorer/invocation.json`, pas `tools/bestiaire/capacites.json`.
  - Coquilles (R10) : `tools/sheets/corrections.json`, section `magie-v10` (sorts, règles et stades d'altération).
- Classes de Décembre (R238, R241, R252, migration 0119, test `db-0119-classes-materiaux-d12.test.mjs`) : 41 classes, 694 capacités ; la règle `classe_imposee` quitte `v_personnage_controle` (`classe_reservee` et `classe_exclue` restent). Les `race_classe.ordre` 40 et 41 sont Boxeur et Porte-étendard, créées hors de la fiche V15.2.2. Une page créée par une migration a son `page_source`, sinon `db:pages-check` et `db:sync-pages` plantent : `tools/db/pages_md.py` (`CLASSEUR_DE_DECEMBRE`) rattache à la famille `classes` les pages qui citent le classeur « Nouveauté mise à jour Décembre ».
- Plafonds de NPM (R188, migration 0097) : `magie_npm_plafond` (Potentiel Illimité → 3) et `capacite_npm_plafond` (`capacites/archimage-semi-complet` → 4). Effet seulement si la magie innée a un plafond : effectif = max(magie, dons acquis), au plus la table des niveaux (R16) ; ne borne que le choix des sorts. `capacite_condition_emplacements` (R189) : lue par le moteur seul. Valeurs jamais lues dans un texte.
- Migration 0099 : `v_arme.solidite_sans_composition` applique le plancher de R51 (au moins 1, R194) ; `invocation.tableau_titre` et `tableau_sort_id` restent, à NULL (skill `zone-bestiaire`). Migration 0100 : ancres figées `{#ancre}` des 20 états de `guide/liste-des-alterations-d-etat` et des 2 sections de la ceinture (skills `zone-magies`, `zone-ceinture`).
- Résistances physiques (R174, migration 0083) : `magie_resistance.cible_type` admet `'physique'`, avec `cible_physique` (`estoc`, `taille`, `frappe`) ; la contrainte nommée `magie_resistance_une_cible` veut exactement une cible renseignée, celle de `cible_type`.
- Migration 0121 (R254 (3), R255 (7), R10, R258 (7), R259, R264 à R266 ; test `db-0121-maj-decembre-suites.test.mjs`) : le registre porte `corrections` (les graphies : skill `base-orthographe`), `cles`, `textes`, `mots_cles` et `evenements`. Mots-clés 410 à 416 (catégories Bestiaire et Combat) : non verrouillés, sans adresse ni couleur (R219 (5)). Événements `gemidiens` (rang 79) et `fongoides` (rang 80), lus dans le registre et mis à part par la chronologie (skill `zone-chronologie`).
- Migration 0123, fusion des pages d'alignement (R271 ; test `db-0123-fusion-pages-alignement.test.mjs`) : `guide/les-neuf-alignements` est retirée dans `guide/alignement`, dont le corps reçoit son texte tel quel sous des ancres figées `{#les-neuf-alignements}` puis `{#loyal-bon}` … `{#chaotique-mauvais}` (les `###` des onglets : skill `zone-guide`) ; ses alias, `page_source` et entrée de menu partent avec elle. Mots-clés 421 à 429 (un par alignement, verrouillés, couleur `alignement:<slug>`, url `/regles/alignement/#<slug>`) ; le 192 garde son id et mène à `#les-neuf-alignements`. Couleur de la page : skill `zone-mots-cles-liens`.

## Tests
Un test par migration ou décision (`db-<NNNN>-…`, `db-r<N>-…` : `ls client/test/db-*`), et : `r160-potentiel-illimite-sans-gemme`, `r188-npm-potentiel-illimite-base`, `db-armes-elementaires` (R167), `db-r181-dons-variables` (état courant : type Variable ⇔ ligne `capacite_variable`, R192 ; le reste à l'import), `db-lexique-en-mots-cles`, `db-liens-en-mots-cles`, `db-rang-des-races`, les `db-retrait-…` (0094 à 0096). Un texte qu'écrit une migration se lit sur son état : `baseDImport({ garder: lotsAvant('NNNN') })` (skill `tests-conventions`). Les tests de `personnage_*` : skill `zone-fiches-base`.
