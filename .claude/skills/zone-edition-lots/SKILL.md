# Lots de changements (site de dev)

## Fichiers
- `lib/lot-de-changements.mjs` : module pur, format `maverick-lot/1` ; livré avec le service (`serveur-livraison`).
- `serveur/edition-lots.mjs` (déposer, lister, lire, essayer, appliquer, refuser), `appliquerUnLot` de `serveur/edition.mjs`, `serveur/controles-du-contenu.mjs` (les contrôles de `db:check`).
- Le service d'édition, le journal et son rejeu : skills `zone-edition`, `zone-edition-rejeu`. La page qui montre les lots : skill `zone-mise-a-jour-lots`.

## À lire
- `docs/serveur.md`, « Lots de changements (format) » et « Lots de changements (service) » : routes, essai à blanc, application, verrous, numéros, annulation, « tout recalculer ». Plan : `docs/chantier-base-de-dev.md`.

## Choix du propriétaire
- R274 : la base du site de dev est la source de vérité.
- R291 (remplace R275 (4)) : un lot déposé par une session qui passe les contrôles (essai à blanc, refus motivés) est appliqué aussitôt ; plus de modification en attente. Le dépôt direct demande la **clé de dépôt** (distincte de la clé de lecture) ; tant qu'elle n'est pas posée, état sûr d'avant : le dépôt est une proposition qui attend le clic du propriétaire (aperçu avant et après). Le propriétaire annule ensuite le lot ou chaque ligne.
- Le lot de changements est **la** voie de l'équipe pour changer le contenu (`CLAUDE.md`). Procédure : skill `modifier-une-page-wiki`.

## Invariants
- `controlerLeLot` reçoit la structure de la base en paramètre ; `comparerAvecLaBase` rend pour chaque opération `applicable` ou `changee` (la valeur a bougé : elle n'est pas écrite, le site prime).
- Un lot ne porte jamais la nature `saisie` (liste des natures : skill `base-sqlite-migrations`, migration 0127). Il refuse les tables de trace (`note_version`, `note_version_ligne`, `historique_modification`). Sur le site de dev (base source, `db/source`, skill `zone-service`), la route (`api.mjs#traiterLots`) donne `ouvertHorsEdition: true` à `controlerLeLot` : un lot vaut pour toutes les tables de contenu (celles que l'édition ne sait pas écrire passent par la voie générique du journal). Sans marqueur, toute table hors `tablesDeLEdition()` (lue dans `edition-modele.mjs`, jamais recopiée) est refusée : `LOT_OUVERT_AUX_TABLES_HORS_EDITION` reste `false` (le défaut du module pur, des tests et de l'épreuve), et aucune autre route ne l'ouvre. Les tables `type_degats` et `monstre_attaque_type` (hors `tablesDeLEdition()`) passent ainsi par la voie générique, sans verrou à lever ; preuve : `serveur-edition-lots-types-attaques` (essai à blanc applicable, écriture au journal). Sur une table connue de l'édition, toute colonne passe : le plan vise « toute colonne que le site ne sait pas écrire ».
- `edition.mjs#appliquerUnLot` ouvre le même `BEGIN IMMEDIATE` qu'`enregistrer` (choix des fiches, notes R42, nature et décision du lot du journal). La voie générique `OPERATIONS_DU_LOT` (`ecrire_modifier`, `ecrire_inserer`, `ecrire_supprimer`) n'est jamais dans `OPERATIONS` ni jointe par une route (une opération inconnue y reste refusée). Une colonne que le service connaît (`TABLES`) s'écrit par son opération ; la voie générique ne sert que pour les autres. L'insertion est refusée dans une table que le service crée lui-même (`ENTITES`), sauf le mot-clé (ci-dessous) ; la suppression d'une entité sans suppression aussi (R159).
- Insertion d'un mot-clé (`traduireLaCreationDUnMotCle`, `edition-lots.mjs`) : le service le crée (id suivant, clé R232), puis `verifier_ligne` (`OPERATIONS_DU_LOT`, jamais jointe par une route) vérifie que la ligne créée est celle que le lot décrit, sinon 409. `verrou` à 1 passe par la colonne tenue (R218, ouverte au clic). Une clé composée reprend un jeton `$numero` déjà donné dans le lot. Test : `serveur-edition-lots-mot-cle`.
- Suppression d'une page : par le service, qui emporte ses lignes dépendantes (le lot ne les porte pas : la ligne serait déjà partie) ; un mot-clé verrouillé qui mène à une page est supprimé avant elle (R221).
- Essai à blanc sur une copie `VACUUM INTO`, supprimée ensuite : `db:check` (`controlerLeContenu`) avant et après, seuls les problèmes nés du lot comptent ; l'application rejoue ces contrôles dans la transaction.
- Une valeur changée entre-temps n'est pas écrite (le site prime) et est listée. Si tout a changé, le lot reste proposé : pas de `modification_lot` vide.
- Dépôt direct (`edition-lots.mjs#deposerEtAppliquer`) : même chemin que le clic (dépôt, essai, `appliquerUnLot`, contrôles rejoués). `bilan.application = { directe, par }` (`cle_de_depot` ou `mot_de_passe`). Un lot refusé au dépôt est enregistré « refuse » avec `bilan` NULL (le CHECK de la base l'exige) et ses motifs dans `essai.refus_du_depot`, exposés en `refus` ; réponse 409, rien n'entre.
- Verrous : un refus du service qui cite un `R…` et que `gel` lève est « verrouillée » ; il ne s'applique que si le numéro est dans `verrous_ouverts` (aujourd'hui R218, R219, R232 (2)). Ouvrir un verrou est **réservé au mot de passe** (R291) : avec la clé de dépôt, `verrous_ouverts` dans le corps donne 403, et un lot qui demande un verrou est « refuse » (409). `COLONNES_TENUES_PAR_LE_SERVICE` (`mot_cle.verrou`, `cle`, `monnaie_id`) refuse la voie générique sous le même gel.
- Numéros : `donnerUnNumero` (`edition-journal.mjs`, avec `plusHautNumero` et `monterLePlafond`), une seule règle pour les lots (jeton `{"$numero": …}`) et l'édition des mots-clés (`idSuivant`, skill `zone-mots-cles-service`) : 1 + max(plafond de `numero_donne`, MAX de la colonne, journal, historique), plafond monté dans la même transaction ; jamais redonné. Pour `mot_cle` : aussi `mot_cle_ancienne_cle` et le registre 0113. Le rejeu d'un ancien journal calcule sans réserver (`monter: false`).
- Annulation (`annulerLeLot` ; `lib/lot-de-changements.mjs#effetNetDuLot`, `jugerLAnnulation`) : le lot du journal est ramené à son effet net ; une valeur n'est remise que si elle vaut encore ce que le lot a écrit (sinon gardée et listée : le site prime). Une insertion n'est supprimée que si elle est intacte ; une suppression est réinsérée à l'identique (`ecrire_inserer` avec `restaurer`, colonnes tenues par le service comprises) seulement si la ligne est absente. Aperçu `GET …/annulation/` sur une copie (Worker), rien n'est écrit ; clic `POST …/annuler/` sous le même `BEGIN IMMEDIATE`, contrôles rejoués. Le journal d'annulation a la nature et la décision du lot ; le résumé est dans `bilan.annulation`. Rien à remettre : 409, le lot reste appliqué. Une annulation ne rend jamais un numéro. Une annulation que refusent les contrôles du contenu (anciens textes fautifs) reste refusée (choix du `leader-technique`).
- Tout recalculer : `recalculerTout` (`POST /api/edition/lots/recalcul/`) dépose un lot de nature `code`, appliqué aussitôt avec la clé de dépôt ou le mot de passe (R291). Périmètre : `TYPES_DE_PAGES_RECALCULEES` (races, classes, fiches de dons, métiers) ; toutes les pages à colonnes dérivées sont comparées. Les magies sont rejouées morceau par morceau (`TABLES_DES_PAGES_PAR_MORCEAUX`, avant = après, `recalculerLesPages`) ; armes, armures et boucliers, potions, « Équipement inventaire » et « Liste d'ingrédients » sont refaits en entier (`refaireLesCorpsEntiers`, appelée par `ecartsDuRecalcul`) ; matériaux, gemmes et bois restent rejoués ligne à ligne (`TABLES_REJOUEES_DES_COMPOSANTS`). Une page dont la section ou le tableau manque est « illisible » (`pages_illisibles`) et reste intacte. Test : `serveur-edition-lots-annulation`. `traduire` envoie une colonne dérivée d'une page typée par la voie générique du journal.
- Annuler une ligne (`annulerUneLigne`, `lignesDuLotApplique`, `dependancesDesLignes`) : une ligne est une ligne de table de l'effet net du lot, pas une colonne (le service réécrit la même ligne plusieurs fois : remettre une colonne seule laisserait des recalculs en désaccord). `n` = rang de sa première écriture au journal du lot, jamais renuméroté. Dépendances statiques par clés étrangères : insertion citée par une autre ligne en place, suppression dont le parent est retiré, page refaite tenue par les autres lignes (`annulable_seule` faux, `motif`, `depend_de`) ; le reste est laissé aux contrôles du contenu. État par ligne dans `bilan.lignes_annulees` ; quand plus aucune ligne n'est en place, le lot passe « annule ». Routes `GET …/lignes/<n>/annulation/` et `POST …/lignes/<n>/annuler/` (mot de passe).
- Écart avec la production : `lister` et `lire` prennent `{ production }` (chemin de la base de référence, `lireReference` dans la route GET des lots) et ajoutent `ecart_production` aux lots `applique` et à chaque ligne du détail. La comparaison (`differeDeLaProduction`) porte sur les colonnes touchées, ligne par ligne, contre la vraie base de production, pas sur `historique_modification` : un lot livré, annulé puis redéposé à l'identique n'y est pas. Page : skill `zone-mise-a-jour-lots` ; test : `serveur-edition-lots-ecart-production`.
- Accès (R291 ; skill `zone-service`) : déposer (clé de dépôt ou mot de passe quand la clé de dépôt est posée, sinon clé de lecture ou mot de passe) et refaire l'essai ; appliquer, refuser, annuler le lot ou une ligne : mot de passe. En production, 403.
