# Conventions des tests

- **Un test par logique.** Toute logique de règle ou de lien nouvelle a son test dans `client/test/` (`node:test`). L'auteur ne lance que le fichier qu'il écrit (`node --test test/<fichier>`) ; la sélection pertinente est passée une seule fois par `tech-qualite`, en fin de lot, jamais la suite entière : skill `choisir-les-tests`. Une décision appliquée est épinglée par un test qui cite son numéro (`R41`).
- **Le site de dev est la source de ce qu'il modifie** (demande du propriétaire ; sa sous-puce « Pas de texte figé » est dans `CLAUDE.md`, « Tests »). Une modification faite sur le site ne fait jamais échouer la suite.
  - **Sur l'état courant**, un test ne lit ni la prose d'un champ modifiable ni la valeur précise d'une colonne modifiable (coût, dés, portée, type… : `src/lib/edition-modele.mjs#TABLES`, `ENTITES`). Il ne vérifie que des invariants : texte lu ou raison portée, CHECK, cohérence entre tables, page ou moteur qui suit la base, ids présents, bloc rendu s'il est présent. Une valeur littérale reste admise quand ni `lib/edition-modele.mjs` ni le service n'écrivent la donnée (`constante_equipement`, `armure_elementaire`) : le test le dit en commentaire.
  - **Sur l'état d'import**, par `test/aide-base-d-import.mjs` : `baseDImport(opts?)` (copie de la base dont chaque modification du site, lue dans `historique_modification`, est défaite ; en lecture seule), `reglesDImport(opts?)`, `cheminDImport(opts?)` (copie pour `preparerBaseVivante({ regles })` ou une base d'essai), `texteDImport(table, cle, colonne, opts?)`. C'est là que se lisent la valeur précise, la phrase d'une décision R… et l'exemple de règle. Une valeur seule se lit aussi par `client/src/lib/historique-site.mjs` (`valeurDImport`, `lignesDImport`, `effectifDImport`). Une colonne qu'une migration a réécrite après le site (le corps des pages `magies/`) n'a plus son texte d'import dans `baseDImport()` : `historiqueSite(db).valeurDImport(table, cle, col)` (patron : `magies-notes.test.mjs#pageDImport`).
  - **Après une migration.** Une phrase que le site a écrite sous une décision, ou qu'une migration a écrite, se lit avec `{ garder: lotsAvant('NNNN') }` : `defaireLeSite` ne défait alors que les lots postérieurs. Le repère n'est pas une date (`fait_le` est l'heure du site) mais la liste figée des `lot_id` présents à la migration (`test/fixtures/lots-avant-NNNN.json`, ex. `lots-avant-0090.json` ; `lectureDe0090` de `db-lexique-en-mots-cles.test.mjs`) : tout lot absent est postérieur. Celui qui écrit une migration qui réécrit un texte lu par les règles ajoute sa fixture. Une balise ou un fragment qu'une migration postérieure a retiré, sans qu'aucun lot du site n'y ait touché, se reconnaît par le registre `textes` de cette migration (`avant` contient l'ancienne écriture, `apres` est dans le texte) : `lotsAvant('NNNN')` ne suffit pas, la base à ce repère portant déjà la migration (patrons : `db-liens-en-mots-cles.test.mjs#baliseOuReecriture`, `test/aide-textes-reecrits.mjs` : `textesReecrits`, `ecrituresReecrites` ; `panneaux-regles.test.mjs`, `equipement.test.mjs`). Un test de registre antérieur (0003, 0004, 0063, 0065) compare l'import hors des lignes qu'une migration réécrit ou supprime, sans liste écrite à la main : `test/aide-migration-0117.mjs` lit le SQL et le registre de la 0117 (`sortsDontLa0117ReecritLes(table)`, `pagesReecritesParLa0117()`), et les effectifs de l'ancien registre se lisent dans lui-même. De même pour des races ajoutées : `test/aide-races-0120.mjs` (`horsDeLa0120`, `MOTS_CLES_DE_LA_0120`, lus dans le registre) met à part les deux races de la 0119 dans les effectifs d'avant elle (0007, 0092 ; R1 : 27 races). Le corps d'une race qu'une migration réécrit après le site se recalcule dans la copie d'import (`lib/corps-races.mjs#corpsDeRace`, `races-magies-innees-liste.test.mjs`) : `defaireLeSite` ne défait pas une cellule réécrite. Un menu courant qui « suit les éditions du site » admet aussi un changement d'onglet (`modifiee(…, 'onglet_id')`). Un texte balisé par le site avant une migration se rend avec le vocabulaire de `lotsAvant('NNNN')` (`fiche-mode-hyper-r187.test.mjs`).
  - **Une page retirée par migration** (0094 à 0096) : les tests `db-retrait-*` cherchent ce qui la cite encore par `test/aide-page-retiree.mjs` (`ecritParLeSite`, `lienDuSite`, `lignesQuiCitent`, `citations`) ; une cellule écrite par le site est admise, et un lien d'un texte que le site a réécrit l'est aussi, mais une adresse retirée écrite par une migration ou par l'import reste interdite. Quand une migration postérieure réécrit le texte que le test lit, il accepte l'une ou l'autre écriture (aide partagée `test/aide-ecritures-du-lien.mjs` : `motsClesVers`, `ecrituresDuLien`, `ecrituresDuTexte`).
  - **Une règle épinglée par une phrase** passe au moteur (ex. R149 : `maitriseDArme`) ou à une colonne non modifiable si elle y vit ; sinon la phrase se lit à l'import, et on le signale (pas de règle figée sur l'état courant).
  - **Chercher par id** (figé), jamais par `nom`, `libelle` ou `nom_cle` sur l'état courant. Un message attendu qui contient un nom se bâtit avec le nom courant lu par id (ou sur une base vivante d'import).
  - **Fichier de règles** : il bascule entier sur l'import, et un test final « aujourd'hui » garde les invariants de la base courante (patron : `fiche-arme-choisie.test.mjs`, `livres.test.mjs`).
  - **Un test `*-html`** vérifie que le HTML rend la base (valeur courante lue par id : libellé du mot-clé…), pas un littéral. Un texte modifiable se compare rendu comme au build, par `test/aide-texte-affiche.mjs` (`premiersMotsAffiches`, `texteAffiche`, `htmlParLignes`, `htmlDuTexteBrut`, `avecLesMotsCles`, `debutDuPanneau`, `verifierLeTexteDuPanneau`), jamais en retirant les marques Markdown à la main (espaces avant la ponctuation). Un texte ou panneau vidé par le site est un cas admis, vérifié.
  - **Un texte précis nécessaire** : le test le pose lui-même dans sa copie de `data/rows` (journal appliqué). Une ligne d'essai (copie, contrainte) se choisit dans l'état courant, pas par un id supposé à sa place d'origine.
  - **Ancres.** L'intertitre visé par un renvoi se vérifie à l'import ; sur l'état courant, le renvoi mène à la bonne page. L'id d'un intertitre courant se calcule comme le build (`lib/guide.mjs#morceauxDuChapitre` rendus par `rendreCommeLeGuide`), jamais par un slug du Markdown brut. Le contrôle affirme une égalité (id présent ⇔ intertitre dans le texte courant) et ne se saute pas (patron : `site-html.test.mjs#verifierLAncre`). Un exemple ne se vérifie jamais sous `if (intacte(...))` : il se vérifie à l'import, et l'état courant garde l'invariant pour toutes les lignes (patron : `classes-html.test.mjs`).
  - **Seuil** (nombre minimal de lignes, effectif attendu…) : il se lit dans l'état d'import (`effectifDImport`, `baseDImport()`), jamais dans la base courante, que le site a pu vider.
  - **Un test ne tombe jamais parce que le site a supprimé une ligne** : il remet ce dont il a besoin (`remettreDepuisLImport`, ci-dessous) ou prend ce qui reste.
  - **Contrôle par mutation** (`npm run mutation -- <variante>` depuis `client/`, `docs/serveur.md` « Contrôle par mutation ») pour un lot qui touche des tests sur la base réelle : il modifie la base par le service d'édition dans une copie jetable, rapatrie le journal, puis lance la suite, qui reste verte. Variantes `temoin` (rien : les échecs de la copie elle-même), `textes`, `noms`, `valeurs`, `adresses`, `suppressions` ; options `--une-sur N` (une ligne sur N de chaque entité), `--garder` (garde la copie pour y relancer un test). Référence d'un lot qui touche aux tests de données : `temoin`, puis `suppressions --une-sur 2`, moins les échecs du témoin. Pas dans la CI.
- **Tests du service.** Ils lisent l'état avant d'écrire et prennent des noms absents de la base (`docs/serveur.md`, « Mise à jour »). Si leurs messages ou exemples citent des noms ou des valeurs de règle, la base vivante part de `cheminDImport()`, si l'état d'import est cohérent pour le service. Sinon (des corps réécrits par migration citent des mots-clés créés par le site, que le service refuse), elle part de la base courante : les lignes du scénario se choisissent dans `baseDImport()` par une clé stable, et le test les remet dans sa copie si le site les a supprimées par `remettreDepuisLImport(db, table, cle, { enfants })` (`test/aide-base-d-import.mjs` : la ligne telle que l'import l'écrit, ses parents et ses enfants sauf `enfants: false` ; patron : `serveur-edition-conflits.test.mjs`). Sans noms cités : recherche par id, noms courants, valeur écrite différente de celle en place. Un test qui applique une mise à jour à `data/rows` et a besoin de lignes que le site a pu retirer les remet dans sa copie des règles et de `data/rows` (patron : `serveur-edition-regles-du-don.test.mjs#remettreLesDonsDImport`).
- **Note de version en attente.** Un test qui lit `data/rows` doit tenir avec une note en attente de livraison (pendant une mise à jour, ou sur `dev` avant la livraison). Il :
  - applique un lot à une copie sans elle (`test/aide-mise-a-jour.mjs#copieSansNoteEnAttente`) ;
  - écrit une note à une version libre (`versionLibre`) ;
  - saute la section 15 quand il balaie tout le texte de la base (`lib/notes-de-version.mjs#TABLES_DES_NOTES`).
- **Site construit.** Les tests `*-html.test.mjs` contrôlent le site construit (`dist/`). Ils se sautent sans `dist/`, et la CI les lance après le build : `tech-qualite` lance `npm run build` avant eux, en fin de lot, quand le rendu change (l'auteur n'en lance pas pour ses tests).
- **Textes balisés.** Un test qui compare un texte « tel qu'écrit » à une sortie qui retire les balises du glossaire lit ce texte sans elles (`texteSansBalises`), ou rend ses balises comme le middleware (`htmlAvecMotsCles`) (`zone-mots-cles`).
- **Vocabulaire.** Les tests du vocabulaire créent leurs mots-clés d'essai, ids 9001 et suivants (`test/aide-mots-cles.mjs#idDEssai`). Un mot-clé réel se cherche par son id entier figé : `aide-mots-cles.mjs#idDuMotCleNomme('<ancien id texte>')` (registre de la 0113), ou `IDS_DES_MOTS_CLES_PROTEGES` / `idDuProtege` pour un protégé ; jamais par sa clé ni par son libellé, que le site de dev change (R232 (2)).
- **Base d'essai.** Un test écrit dans une copie de la base, jamais dans `var/maverick.db` ni dans `data/rows`.
- **Base vivante.** `preparerBaseVivante({ garderLeSite: false })` (`serveur/base-vivante.mjs`) est réservé aux tests qui éprouvent la résolution des lots annulés (ancienne forme) ; sinon les lots ambigus sont gardés et les conflits réévalués.
- **Dossiers temporaires.** Un test fait le ménage quand il a fini, même en cas d'échec (demande du propriétaire). Ses dossiers et fichiers temporaires (copies de base, exports, faux dépôts) viennent de `test/aide-dossier-temporaire.mjs` :
  - `dossierTemporaire(prefixe, { t })` le supprime à la fin du test `t` (contexte d'un test, ou de `beforeEach` pour un dossier par cas) ;
  - sans `t`, il est supprimé à la sortie du processus du fichier, après ses hooks `after` ;
  - `fichierTemporaire(nom, prefixe, options)` donne un chemin dans un dossier neuf, `dans` place le dossier sous un autre ;
  - `variablesTemporaires(dossier)` donne le dossier de l'aide à un script, un outil ou un service lancé par le test (`TMPDIR`).
  - Un fichier qui crée beaucoup de copies (`serveur-base-vivante`) prend un dossier par cas. Garde-fou `dossiers-temporaires.test.mjs` : refuse hors de l'aide `mkdtemp`, `os.tmpdir()`, `/tmp`, `/var/tmp`, `/dev/shm`, `TMPDIR`, `tempfile` (`.py`), `mktemp` (`.sh`). Une exception s'y inscrit, raison dite.
- **Jamais** sauter, désactiver ni mettre en quarantaine un test pour obtenir du vert.
