# Conventions des tests

- **Un test par logique.** Toute logique de règle ou de lien nouvelle a son test dans `client/test/` (`node:test`). L'auteur ne lance que le fichier qu'il écrit (`node --test test/<fichier>`) ; la sélection pertinente est passée une seule fois par `tech-qualite`, en fin de lot, jamais la suite entière : skill `choisir-les-tests`. Une décision appliquée est épinglée par un test qui cite son numéro (`R41`).
- **Le site de dev est la source de ce qu'il modifie** (demande du propriétaire ; sa sous-puce « Pas de texte figé » est dans `CLAUDE.md`, « Tests »). Une modification faite sur le site ne fait jamais échouer la suite.
  - **Sur l'état courant**, un test ne lit ni la prose d'un champ modifiable ni la valeur précise d'une colonne modifiable (coût, dés, portée, type… : `src/lib/edition-modele.mjs#TABLES`, `ENTITES`). Il ne vérifie que des invariants : chaque texte est lu ou porte une raison, CHECK, cohérence entre tables, la page ou le moteur suit la base, ids présents, bloc rendu s'il est présent. Une valeur littérale reste admise quand ni `lib/edition-modele.mjs` ni le service n'écrivent la donnée (`constante_equipement`, `armure_elementaire`, ses améliorations de cible) : le test le dit dans un commentaire.
  - **Sur l'état d'import**, par `test/aide-base-d-import.mjs` : `baseDImport(opts?)` (copie de la base dont chaque modification du site, lue dans `historique_modification`, est défaite ; en lecture seule), `reglesDImport(opts?)`, `cheminDImport(opts?)` (copie pour `preparerBaseVivante({ regles })` ou une base d'essai), `texteDImport(table, cle, colonne, opts?)`. C'est là que se lisent la valeur précise, la phrase d'une décision R… et l'exemple de règle. Une valeur seule se lit aussi par `client/src/lib/historique-site.mjs` (`valeurDImport`, `lignesDImport`, `effectifDImport`). Une colonne qu'une migration a réécrite après le site (le corps des pages `magies/`) n'a plus son texte d'import dans `baseDImport()` : `historiqueSite(db).valeurDImport(table, cle, col)` (patron : `magies-notes.test.mjs#pageDImport`).
  - **Après une migration.** Une phrase que le site a écrite sous une décision, ou qu'une migration a écrite, se lit avec `{ garder: lotsAvant('NNNN') }` : `defaireLeSite` ne défait alors que les lots postérieurs. Le repère n'est pas une date (`fait_le` est l'heure du site de dev, pas celle du rapatriement) mais la liste figée des `lot_id` présents à la migration (`lots-avant-NNNN.json`, ex. `test/fixtures/lots-avant-0090.json`, `lots-avant-0095.json` ; `lectureDe0090` de `db-lexique-en-mots-cles.test.mjs`) : tout lot absent est postérieur. Celui qui écrit une migration qui réécrit un texte lu par les règles ajoute sa fixture. Un menu courant qui « suit les éditions du site » admet aussi un changement d'onglet (`modifiee(…, 'onglet_id')`). Un texte balisé par le site avant une migration se rend avec le vocabulaire de `lotsAvant('NNNN')`, pas celui de l'import pur, où manque un mot-clé créé par le site (`chakra`, `fiche-mode-hyper-r187.test.mjs`).
  - **Une page retirée par migration** (0094 à 0096) : les tests `db-retrait-*` cherchent ce qui la cite encore par `test/aide-page-retiree.mjs` (`ecritParLeSite`, `lienDuSite`, `lignesQuiCitent`, `citations`) ; une cellule écrite par le site est admise, et un lien d'un texte que le site a réécrit l'est aussi, mais une adresse retirée écrite par une migration ou par l'import reste interdite. Quand une migration postérieure réécrit le texte que le test lit (les liens devenus balises), il accepte l'une ou l'autre écriture sans figer la forme postérieure (aide partagée `test/aide-ecritures-du-lien.mjs` : `motsClesVers`, `ecrituresDuLien`, `ecrituresDuTexte`).
  - **Une règle épinglée par une phrase** passe au moteur (ex. R149 : `maitriseDArme`) ou à une colonne non modifiable si elle y vit ; sinon la phrase se lit à l'import, et on le signale (pas de règle figée sur l'état courant).
  - **Chercher par id** (figé), jamais par `nom`, `libelle` ou `nom_cle` sur l'état courant. Un message attendu qui contient un nom se bâtit avec le nom courant lu par id (ou sur une base vivante d'import).
  - **Fichier de règles** : il bascule entier sur l'import, et un test final « aujourd'hui » garde les invariants de la base courante (patron : `fiche-arme-choisie.test.mjs`, `livres.test.mjs`).
  - **Un test `*-html`** vérifie que le HTML rend la base (valeur courante lue par id : libellé du mot-clé…), pas un littéral. Un texte modifiable se compare rendu comme au build, par `test/aide-texte-affiche.mjs` (`premiersMotsAffiches`, `texteAffiche`, `htmlParLignes`, `htmlDuTexteBrut`, `avecLesMotsCles`, `debutDuPanneau`, `verifierLeTexteDuPanneau`), jamais en retirant les marques Markdown à la main (espaces avant la ponctuation). Un texte ou un panneau vidé par le site est un cas admis, vérifié explicitement.
  - **Un texte précis nécessaire** : le test le pose lui-même dans sa copie de `data/rows` (journal appliqué). Une ligne d'essai (copie, contrainte) se choisit dans l'état courant, pas par un id supposé à sa place d'origine.
  - **Ancres.** L'intertitre visé par un renvoi se vérifie à l'import ; sur l'état courant, le renvoi mène à la bonne page. L'id d'un intertitre courant se calcule comme le build (`lib/guide.mjs#morceauxDuChapitre` rendus par `rendreCommeLeGuide`), jamais par un slug du Markdown brut. Le contrôle affirme toujours une égalité (id présent ⇔ intertitre dans le texte courant), il ne se saute pas (patron : `site-html.test.mjs#verifierLAncre`). Un exemple ne se vérifie jamais sous `if (intacte(...))` : il se vérifie à l'import, et l'état courant garde l'invariant pour toutes les lignes (patron : `classes-html.test.mjs`).
  - **Seuil** (nombre minimal de lignes, effectif attendu…) : il se lit dans l'état d'import (`effectifDImport`, `baseDImport()`), jamais dans la base courante, que le site a pu vider.
  - **Un test ne tombe jamais parce que le site a supprimé une ligne** : il remet ce dont il a besoin (`remettreDepuisLImport`, ci-dessous) ou prend ce qui reste.
  - **Contrôle par mutation** (`npm run mutation -- <variante>` depuis `client/`, `docs/serveur.md` « Contrôle par mutation ») pour un lot qui touche des tests sur la base réelle : il modifie la base par le service d'édition dans une copie jetable, rapatrie le journal, puis lance la suite, qui reste verte. Variantes `temoin` (rien : les échecs de la copie elle-même), `textes`, `noms`, `valeurs`, `adresses`, `suppressions` ; options `--une-sur N` (une ligne sur N de chaque entité), `--garder` (garde la copie pour y relancer un test). Passage de référence d'un lot qui touche aux tests de données : `temoin`, puis `suppressions --une-sur 2` ; on retranche les échecs du témoin. Pas dans la CI.
- **Tests du service.** Ils lisent l'état avant d'écrire et prennent des noms absents de la base (`docs/serveur.md`, « Mise à jour »). Si leurs messages ou exemples citent des noms ou des valeurs de règle, la base vivante part de `cheminDImport()`, si l'état d'import est cohérent pour le service. Sinon (des corps réécrits par migration citent des mots-clés créés par le site, que le service refuse), elle part de la base courante : les lignes du scénario se choisissent dans `baseDImport()` par une clé stable, et le test les remet dans sa copie si le site les a supprimées par `remettreDepuisLImport(db, table, cle, { enfants })` (`test/aide-base-d-import.mjs` : la ligne telle que l'import l'écrit, ses parents, et ses enfants sauf `enfants: false` ; patron : `serveur-edition-conflits.test.mjs`). Sans noms cités : recherche par id, noms courants, et valeur écrite différente de celle en place. Un test qui applique une mise à jour à `data/rows` et a besoin de lignes que le site a pu retirer les remet dans sa copie des règles et de `data/rows`, pour tenir sous une modification libre du site de dev (patron : `serveur-edition-regles-du-don.test.mjs#remettreLesDonsDImport`).
- **Note de version en attente.** Un test qui lit `data/rows` doit tenir avec une note en attente de livraison (pendant une mise à jour, ou sur `dev` avant la livraison). Pour cela, il :
  - applique un lot à une copie sans elle (`test/aide-mise-a-jour.mjs#copieSansNoteEnAttente`) ;
  - écrit une note à une version libre (`versionLibre`) ;
  - saute la section 15 quand il balaie tout le texte de la base (`lib/notes-de-version.mjs#TABLES_DES_NOTES`).
- **Site construit.** Les tests `*-html.test.mjs` contrôlent le site construit (`dist/`). Ils se sautent sans `dist/`, et la CI les lance après le build : `tech-qualite` lance `npm run build` avant eux, en fin de lot, quand le rendu change (l'auteur n'en lance pas pour ses tests).
- **Textes balisés.** Un test qui compare un texte « tel qu'écrit » à une sortie qui retire les balises du glossaire lit ce texte sans elles (`texteSansBalises`), ou rend ses balises comme le middleware (`htmlAvecMotsCles`) (`zone-mots-cles`).
- **Vocabulaire.** Les tests du vocabulaire créent leurs mots-clés d'essai (`test/aide-mots-cles.mjs`).
- **Base d'essai.** Un test écrit dans une copie de la base, jamais dans `var/maverick.db` ni dans `data/rows`.
- **Dossiers temporaires.** Un test fait le ménage quand il a fini, même en cas d'échec (demande du propriétaire, 2026-10-23). Ses dossiers et fichiers temporaires (copies de base, exports, faux dépôts) viennent de `test/aide-dossier-temporaire.mjs` :
  - `dossierTemporaire(prefixe, { t })` le supprime à la fin du test `t` (contexte d'un test, ou de `beforeEach` pour un dossier par cas) ;
  - sans `t`, il est supprimé à la sortie du processus du fichier, après ses hooks `after` ;
  - `fichierTemporaire(nom, prefixe, options)` donne un chemin dans un dossier neuf, `dans` place le dossier sous un autre ;
  - `variablesTemporaires(dossier)` donne le dossier de l'aide à un script, un outil ou un service lancé par le test (`TMPDIR`).
  - Le garde-fou `test/dossiers-temporaires.test.mjs` refuse dans `client/test/` tout `mkdtemp`, `os.tmpdir()`, chemin `/tmp`, `/var/tmp` ou `/dev/shm`, lecture de `TMPDIR` (destructuration comprise), `tempfile` dans un `.py` ou `mktemp` dans un `.sh` hors de l'aide. Une exception s'y inscrit avec sa raison.
  - Un fichier qui crée beaucoup de copies (`serveur-base-vivante`) en prend un dossier par cas.
- **Jamais** sauter, désactiver ni mettre en quarantaine un test pour obtenir du vert.
