# Conventions des tests

- **Un test par logique.** Toute logique de règle ou de lien nouvelle a son test dans `client/test/` (`node:test`). L'auteur ne lance que le fichier qu'il écrit (`node --test test/<fichier>`) ; la sélection est passée une seule fois par `tech-qualite`, en fin de lot : skill `choisir-les-tests`. Une décision appliquée est épinglée par un test qui cite son numéro (`R41`).
- **Le site de dev est la source du contenu** (R274 ; sa sous-puce « Pas de texte figé » est dans `CLAUDE.md`, « Tests »). Une modification faite sur le site ne fait jamais échouer la suite.
  - **Sur l'état courant**, un test ne lit ni la prose d'un champ modifiable ni la valeur précise d'une colonne modifiable (coût, dés, portée, type… : `src/lib/edition-modele.mjs#TABLES`, `ENTITES`). Il ne vérifie que des invariants : texte lu ou raison portée, CHECK, cohérence entre tables, page ou moteur qui suit la base, ids présents, bloc rendu s'il est présent. Une valeur littérale reste admise quand ni `lib/edition-modele.mjs` ni le service n'écrivent la donnée (`constante_equipement`, `armure_elementaire`) : le test le dit.
  - **Sur l'état d'import**, par `test/aide-base-d-import.mjs` : `baseDImport(opts?)` (copie de la base dont chaque modification du site, lue dans `historique_modification`, est défaite ; en lecture seule), `reglesDImport(opts?)`, `cheminDImport(opts?)` (copie pour `preparerBaseVivante({ regles })` ou une base d'essai), `texteDImport(table, cle, colonne, opts?)`. C'est là que se lisent la valeur précise, la phrase d'une décision R… et l'exemple de règle. Une valeur seule : `lib/historique-site.mjs` (`valeurDImport`, `lignesDImport`, `effectifDImport`). Seules les traces de nature `saisie` et `decision` sont « le site » (`NATURES_DEFAITES` ; `lireHistorique`, `defaireLeSite`, `valeurDImport`) ; `source`, `migration` et `code` font partie de l'état d'import. Sans `nature`, une trace se lit comme `saisie`. `valeursDAvant` lit toutes les natures. Une colonne qu'une migration a réécrite après le site (le corps des pages `magies/`) se lit par `historiqueSite(db).valeurDImport(table, cle, col)` (patron : `magies-notes.test.mjs#pageDImport`).
  - **Après une migration.** Une phrase que le site a écrite sous une décision, ou qu'une migration a écrite, se lit avec `{ garder: lotsAvant('NNNN') }` : `defaireLeSite` ne défait alors que les lots postérieurs. Le repère est la liste figée des `lot_id` présents à la migration (`test/fixtures/lots-avant-NNNN.json`), pas une date ; une migration qui réécrit un texte lu par les règles ajoute sa fixture. Un fragment qu'une migration postérieure a retiré sans lot du site se reconnaît par le registre `textes` de cette migration (`avant`, `apres`) : patrons `db-liens-en-mots-cles.test.mjs#baliseOuReecriture`, `test/aide-textes-reecrits.mjs` (`textesReecrits`, `ecrituresReecrites`). Un test de registre antérieur compare l'import hors des lignes qu'une migration réécrit ou supprime : `test/aide-migration-0117.mjs`, `test/aide-races-0120.mjs`. Le corps d'une race réécrit après le site se recalcule dans la copie d'import (`lib/corps-races.mjs#corpsDeRace`) ; une cellule réécrite par le registre `textes` se défait par `aide-base-d-import.mjs#avantReecrit` (0122). Un menu courant admet un changement d'onglet (`modifiee(…, 'onglet_id')`). Un texte balisé avant une migration se rend avec le vocabulaire de `lotsAvant('NNNN')` (`fiche-mode-hyper-r187.test.mjs`).
  - **Sortie du contenu** (R296 ; `src/lib/sortie-du-contenu.mjs` : `CONTENU_SORTI = false`, `contenuSorti(env)`, `MAVERICK_CONTENU_SORTI=1`). L'interrupteur est allumé par la PR du jour J et par la passe S de l'essai mécanique ; éteint, rien ne change.
    - Un test qui ne vaut que tant que le contenu est dans le dépôt (il éprouve une migration de données, un registre, `data/rows` ou un extracteur qui sortent) se déclare par `test/aide-sortie-du-contenu.mjs#testRetireAvecLeContenu(import.meta.url)` et s'inscrit dans `RETIRES_AVEC_LE_CONTENU` avec sa raison (`sortie-du-contenu.test.mjs` vérifie l'accord). Seulement si ce qu'il éprouve sort, jamais pour obtenir du vert.
    - Un registre qui sort et que des tests d'invariants lisent encore se lit par `test/aide-registres-sortis.mjs#registreDeMigration(nom)` (gardé dans `test/fixtures/registres-sortis.json`, sans texte), jamais par `data/migrations/<nom>.json` en direct (patron : `guide-sans-chapitres.test.mjs`, la 0064 : ids, chapitres, parties).
    - Un test qui lit les exports passe par `dossierDesExports()` (`tools/sources/dossier-des-exports.mjs`), jamais par `sources/raw` en dur.
  - **Une migration qui cite une ligne créée par le site** (une clé étrangère vers un mot-clé que l'import n'a pas, ex. `type_degats.mot_cle_id`, 0125) : la référence se déclare dans `test/aide-base-d-import.mjs#REFERENCES_DES_MIGRATIONS` (table citée → [table, colonne nullable]) ; `defaireLeSite` la met à NULL avant de retirer la ligne. Sans elle, `baseDImport` refuse la copie (clés étrangères rompues).
  - **Une page retirée par migration** (0094 à 0096) : les tests `db-retrait-*` cherchent ce qui la cite encore par `test/aide-page-retiree.mjs` ; une cellule ou un lien écrit par le site est admis, une adresse retirée écrite par une migration ou par l'import reste interdite. Quand une migration postérieure réécrit le texte lu, le test accepte l'une ou l'autre écriture (`test/aide-ecritures-du-lien.mjs` : `motsClesVers`, `ecrituresDuLien`, `ecrituresDuTexte`).
  - **Une règle épinglée par une phrase** passe au moteur (ex. R149 : `maitriseDArme`) ou à une colonne non modifiable si elle y vit ; sinon la phrase se lit à l'import, et on le signale.
  - **Une valeur liée** (type de dégâts, mot-clé…) : le test vérifie l'état courant sans supposer qu'un cas existe ; chaque branche (liée, non liée…) se couvre sur une copie temporaire modifiée (patron : `mots-cles-des-valeurs.test.mjs`).
  - **Chercher par id** (figé), jamais par `nom`, `libelle` ou `nom_cle` sur l'état courant. Un message attendu qui cite un nom se bâtit avec le nom courant lu par id.
  - **Fichier de règles** : il bascule entier sur l'import, et un test final « aujourd'hui » garde les invariants de la base courante (patron : `fiche-arme-choisie.test.mjs`, `livres.test.mjs`).
  - **Un test `*-html`** vérifie que le HTML rend la base (valeur courante lue par id : libellé du mot-clé…), pas un littéral. Un texte modifiable se compare rendu comme au build, par `test/aide-texte-affiche.mjs`, jamais en retirant les marques Markdown à la main (espaces avant la ponctuation). Un texte ou panneau vidé par le site est un cas admis, vérifié.
  - **Un texte précis nécessaire** : le test le pose dans sa copie de `data/rows` (journal appliqué) ; une ligne d'essai se choisit dans l'état courant, pas par un id supposé.
  - **Ancres.** L'intertitre visé par un renvoi se vérifie à l'import ; sur l'état courant, le renvoi mène à la bonne page. L'id d'un intertitre courant se calcule comme le build (`lib/guide.mjs#morceauxDuChapitre` rendus par `rendreCommeLeGuide`), jamais par un slug du Markdown brut. Le contrôle affirme une égalité (id présent ⇔ intertitre dans le texte courant), sans saut (patron : `site-html.test.mjs#verifierLAncre`). Un exemple ne se vérifie jamais sous `if (intacte(...))` : à l'import, avec l'invariant sur toutes les lignes courantes (patron : `classes-html.test.mjs`).
  - **Seuil** (nombre minimal de lignes, effectif attendu…) : lu dans l'état d'import (`effectifDImport`, `baseDImport()`), jamais dans la base courante, que le site a pu vider. Un test ne tombe jamais parce que le site a supprimé une ligne : il remet ce dont il a besoin (`remettreDepuisLImport`, ci-dessous) ou prend ce qui reste.
  - **Contrôle par mutation** (`npm run mutation -- <variante>` depuis `client/`) pour un lot qui touche des tests sur la base réelle : le service d'édition modifie une copie jetable ; la suite doit rester verte. Variantes, options et référence (`temoin`, puis `suppressions --une-sur 2`) : `docs/serveur.md`, « Contrôle par mutation ». Pas dans la CI.
- **Tests du service.** Ils lisent l'état avant d'écrire et prennent des noms absents de la base (`docs/serveur.md`, « Mise à jour »). Si leurs messages ou exemples citent des noms ou des valeurs de règle, la base vivante part de `cheminDImport()` quand l'état d'import est cohérent pour le service ; sinon (des corps réécrits par migration citent des mots-clés créés par le site, que le service refuse), de la base courante : les lignes du scénario se choisissent dans `baseDImport()` par une clé stable et se remettent dans la copie par `remettreDepuisLImport(db, table, cle, { enfants })` (`aide-base-d-import.mjs` ; patron : `serveur-edition-conflits.test.mjs`). Sans noms cités : recherche par id, noms courants, valeur écrite différente de celle en place. Un test qui applique une mise à jour à `data/rows` remet de même les lignes retirées par le site (patron : `serveur-edition-regles-du-don.test.mjs#remettreLesDonsDImport`).
- **Note de version en attente.** Un test qui lit `data/rows` doit tenir avec une note en attente de livraison (pendant une mise à jour, ou sur `dev` avant la livraison). Il :
  - applique un lot à une copie sans elle (`test/aide-mise-a-jour.mjs#copieSansNoteEnAttente`) ;
  - écrit une note à une version libre (`versionLibre`) ;
  - saute la section 15 quand il balaie tout le texte de la base (`lib/notes-de-version.mjs#TABLES_DES_NOTES`).
- **Site construit.** Les tests `*-html.test.mjs` contrôlent le site construit (`dist/`). Ils se sautent sans `dist/`, et la CI les lance après le build : `tech-qualite` lance `npm run build` avant eux, en fin de lot, quand le rendu change (l'auteur n'en lance pas pour ses tests).
- **Textes balisés.** Un test qui compare un texte « tel qu'écrit » à une sortie sans les balises du glossaire lit ce texte sans elles (`texteSansBalises`), ou les rend comme le middleware (`htmlAvecMotsCles`) (`zone-mots-cles`).
- **Vocabulaire.** Les tests du vocabulaire créent leurs mots-clés d'essai, ids 9001 et suivants (`test/aide-mots-cles.mjs#idDEssai`). Un mot-clé réel se cherche par son id entier figé : `aide-mots-cles.mjs#idDuMotCleNomme('<ancien id texte>')` (registre de la 0113), ou `IDS_DES_MOTS_CLES_PROTEGES` / `idDuProtege` pour un protégé ; jamais par sa clé ni par son libellé, que le site de dev change (R232 (2)).
- **Aucune donnée de joueur ne sort.** Pour un fichier que le service laisse sortir (extrait, attestation), `test/aide-fiches-sentinelles.mjs` pose des fiches, un compte et un groupe aux noms sentinelles (`poserDesFiches`, `marquesDesFiches`) que le test cherche dans chaque octet produit.
- **Fabrication depuis un extrait.** `aide-contenu-fourni.mjs` : `extraitDEssai()` (un par processus), `copieDEssai(dossier, modifier)` (copie que `modifier(db)` change).
- **Test de nature « dépôt »** (`db:pages-check`, `db:build` sur `data/rows`, mise à jour ou copie qui écrit `data/rows`) : la CI lance `npm test` sous l'extrait (`MAVERICK_CONTENU`) avec `data/rows` présent, et `client/src/content/wiki` vient alors de l'extrait. Le test retire `MAVERICK_CONTENU` et `MAVERICK_CONTENU_DERIVE` de l'environnement des processus lancés, exporte son wiki de référence depuis `data/rows` dans un dossier temporaire (`db-export-pages --out`) et bâtit sa base par `baseDeDepart(dest, { deriver: true, rows: ROWS })` (patron : `mise-a-jour-paquet.test.mjs`) ; `db-donnees.test.mjs` lance `db-build` sur `data/rows`, sans la variable.
- **Base d'essai.** Un test écrit dans une copie, jamais dans `var/maverick.db` ni `data/rows`. Un test qui fabrique sa base remplie ou copie `data/rows` passe par `test/aide-base-de-depart.mjs` (`baseDeDepart`, `rowsDeDepart`, `copieDesRowsDeDepart`), qui lit le contenu fourni (`MAVERICK_CONTENU`) : jamais `db-build` ni `cpSync(data/rows)` en direct. L'invariant « tables propres au site vides » se vérifie par `aide-base-de-depart.mjs#lignesDuContenu`, jamais en lisant `data/rows`.
- **Essai mécanique** (`scripts/essai-mecanique-tests.mjs`, `docs/essai-mecanique-des-tests.md`) : chaque fichier de test est lancé seul sur plusieurs contenus, dont la passe C (l'extrait du site de dev, sans `data/rows`) et les variantes V1 à V4.
  - Les variantes sont des saisies fidèles au site (par le service, ou une trace `saisie`), sur ce que `edition-modele.mjs` rend modifiable seulement. Un test qui casse sur une Vn fige une valeur modifiable.
  - V5 (magie renommée, hors des voies du site) est informative. La preuve qu'une donnée n'est pas modifiable est un test de refus par `enregistrer` (`serveur-edition-nom-de-magie`).
  - `LIT_LE_DEPOT_PAR_NATURE` ne liste plus que ce qui lit `data/rows` (`db:build`, mise à jour ou copie qui l'écrit, fichier des pages d'exemple), avec sa raison : son échec sur C est attendu tant que `data/rows` est dans le dépôt.
  - Passe D : les fichiers de `LIT_LE_DEPOT_PAR_NATURE` avec `data/rows` ET l'extrait en `MAVERICK_CONTENU`, comme la CI. Un échec y est rouge.
  - Passe S : l'extrait pour contenu dans une copie sans ce qui sortira du dépôt (catégories de `scripts/inventaire-sortie-du-contenu-lib.mjs#listerCeQuiSort` ; `--avec-mixtes` y ajoute les migrations mixtes), allumée (`environnementDeLaPasse` : `MAVERICK_CONTENU_SORTI=1`, `MAVERICK_SOURCES_RAW` et `MAVERICK_MIGRATIONS_ARCHIVEES` vers des archives `git archive` des exports et des migrations). Aucune rubrique « par nature » : tout échec est rouge. Verte, elle est le critère de fin du lot 12. `node scripts/essai-mecanique-tests.mjs --passe S [--avec-mixtes] [--controles]`, puis `--trier`.
  - `--passe <P> --controles` construit le site dans la copie et y lance les tests du site construit (en S, sans `db:build`, qui lit `data/rows`).
- **`data/rows` n'est écrit par aucune PR** (`controle-du-contenu-ecrit`), hors l'export qu'une migration de structure permet (ses tables, `data/rows/VERSION`, les tables qui gardent des noms pour un renommage : `docs/flux-git.md`, « Contenu écrit à la main ») : c'est la copie du site de dev, tenue par « Copier vers le dépôt » et chaque mise à jour (R278). Un contenu qui n'y est pas encore attend la copie du jour.
- **Base remplie.** `client/scripts/base-remplie-lib.mjs` génère une base avec fiches, journal et historique (le contrôle des migrations et `test/aide-structure-sur-place.mjs` l'importent ; `NUMERO` y est calculé et `annulerLesMigrations(db)` défait la structure des migrations livrées depuis `NUMERO` : une nouvelle migration de structure ne demande rien à ces tests). `aide-structure-sur-place.mjs#baseDesRegles` vide les tables et colonnes ajoutées depuis `NUMERO` (une table que le site remplit ne fait pas rougir l'essai) et suit les colonnes de `personnage` et `utilisateur`.
- **Base vivante.** `preparerBaseVivante({ garderLeSite: false })` (`serveur/base-vivante.mjs`) est réservé aux tests de la résolution des lots annulés (ancienne forme).
- **Dossiers temporaires.** Un test fait le ménage quand il a fini, même en cas d'échec (demande du propriétaire). Ses dossiers et fichiers temporaires viennent de `test/aide-dossier-temporaire.mjs` :
  - `dossierTemporaire(prefixe, { t })` le supprime à la fin du test `t` (ou de `beforeEach`, un dossier par cas) ; sans `t`, à la sortie du processus du fichier, après ses hooks `after` ;
  - `fichierTemporaire(nom, prefixe, options)` donne un chemin dans un dossier neuf, `dans` place le dossier sous un autre ;
  - `variablesTemporaires(dossier)` donne le dossier de l'aide à un script, un outil ou un service lancé par le test (`TMPDIR`).
  - Un fichier qui crée beaucoup de copies (`serveur-base-vivante`) prend un dossier par cas. Garde-fou `dossiers-temporaires.test.mjs` : refuse hors de l'aide `mkdtemp`, `os.tmpdir()`, `/tmp`, `TMPDIR`, `tempfile`, `mktemp`. Une exception s'y inscrit, raison dite.
- **Sauvegardes** (`deploy-sauvegardes*.test.mjs`). `test/aide-sauvegardes.mjs` fournit un monde factice, un faux docker et un restic espion ; les tests restic se sautent sans restic, ceux de bash, sqlite3 et flock aussi.
- **Jamais** sauter, désactiver ni mettre en quarantaine un test pour obtenir du vert.
